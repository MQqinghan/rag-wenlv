## 〇、升级规划的最终目的（终局目标）

> 本升级规划所有事项（A 导入治理 / B 意图路由 / C 规划并行）最终都服务于以下目标。任何一项改造完成度的判定，都应回到这些目标是否被满足。

1. **生成让用户满意的旅游规划**：行程规划（事项 C 及其与检索 / 天气 / 路线的衔接）的终局判别标准是「用户拿到手即用得上、愿意照着走」，而非「跑通了一条图链路」。
2. **意图识别精准**：对话必须准确识别用户意图，明确区分两类——**旅游**（景点 / 行程 / 路线 / 酒店 / 美食等实操诉求）、**文化介绍**（历史 / 民俗 / 非遗 / 风土人情等介绍类诉求），并据此路由到正确的检索与生成链路。（注：现有架构把"文化介绍"归入文旅 `tourism` 域，升级后意图识别需能区分"旅游实操"与"文化介绍"两类诉求。）
3. **模糊问题可解**：能够利用上下文记忆理解用户的模糊问题（如指代、延续类追问、省略主体的短问句），不靠用户把每句话都说完整。
4. **移动端可触达（新增 · 2026-09-09，形态：微信小程序优先）**：检索生成这一端最终要部署到手机上（**以微信小程序为优先形态**，独立 APP 作为后续可选项），让用户随时随地用自然语言 / 图片提问，并在弱网下稳定交互。**这是贯穿性终局目标：自本规划修订起，所有后续优化与代码修改都应以"可上手机"为前置约束**（具体约束见下方「移动端部署前置约束」）。

#### 移动端部署前置约束（所有后续改造必须遵守）
> 自 2026-09-09 起生效。A / B / C 三系及任何新增改造，在方案设计、代码评审、落地验收时均须满足以下约束——这是把终局目标转化为可执行纪律的关键。

1. **服务端重、客户端轻**：Milvus / BGE-M3 / 大模型推理全部留在服务端；手机端只承载 UI、输入采集、结果展示。后续优化不得将重逻辑下沉到前端。
2. **必须建设 BFF / 网关层**：统一鉴权（`user_id` 长期记忆的前提）、限流、会话管理、协议转换；网关同时承接分层防护（输入校验 / 越权拦截 / 输出护栏）。
3. **流式协议兼容 WebSocket + SSE（微信小程序优先 → WebSocket 为主）**：现有流式以 SSE 实现（技术栈已用）；微信小程序对 SSE 长连接支持受限，移动端主链路以 **WebSocket（WSS）流式** 为准，SSE 保留用于 Web / 独立 APP。微信小程序须配置**备案域名 + HTTPS/WSS**，后端入口需支持 WSS 接入（由 BFF 网关承接）。
4. **输入多态与噪声鲁棒**：移动端首输入常为拍照（VL，已用）。图片文本含手写、错别字、模糊噪声 → **反向强化 B1 意图路由 LLM 化**（正则难扛噪声），后续路由改造须以 LLM 主导为默认。
5. **弱网 / 离线降级**：请求重试、超时、答案缓存（呼应已落地的语义缓存 + 待做的 Redis）、断点续传；任何新增外部依赖须有降级路径。
6. **隐私合规与脱敏**：用户数据上云须加密、脱敏（呼应 A3 / A4 外发治理）；移动端隐私监管更严，外发治理优先级抬升。
7. **包体与首屏**：前端极简、资源懒加载，控制微信小程序主包 / 分包体积。

### 远期追加项（非紧急，主人明确"不着急做"）

- **长期记忆**：在现有单会话窗口记忆之外，按 `user_id` 持久化保存记忆，使跨会话的用户偏好、历史行程、常访地点等可复用，而不仅限于一个会话窗口。**（是手机端跨会话个性化的基础，移动端部署使其从"有就好"升级为"必须有"。）**
- **Redis 缓存降本增效**：评估引入 Redis 缓存机制（向量检索结果、LLM 改写 / 路由结果、热门问答等），降低重复请求的 LLM / 检索开销。**（移动端多用户 / 弱网场景价值放大——已落地的进程内语义缓存是第一步，Redis 是多 worker / 重启后全局共享的下一步。）**
- **分层防护策略**：建立分层防护策略（输入校验 / 敏感词与越权拦截 / 输出护栏 / 外发网关白名单等）预防提示词攻击（prompt injection）。**（移动端暴露面广，此项优先级随手机端部署抬升。）**
- **Hermes Agent 范式借鉴（已纳入正式优化方向 · 2026-09-09 拍板）**：参考 Nous Research 开源 Hermes Agent（2026-02 发布，MIT，~40k★）的可用范式，**不引入其框架本体**，仅借鉴范式融入既有事项——① **否决式模型路由** → 落地到 **B1**（B1 单次 LLM 调用输出 `source_policy` 时，对简单问判定走语义缓存 / 廉价模型，复杂规划才走大模型；保守否决式，宁贵勿错；呼应 B1 + Redis 降本）；② **多平台消息网关** → 落地到 **移动端 BFF 网关**（单一网关承接微信小程序 / 后续钉钉飞书，正是手机端接入范式）；③ **主动持久记忆 + 辩证式用户建模** → 落地到 **长期记忆（按 user_id）**（跨会话偏好 / 历史行程累积，可借鉴 Honcho 正-反-合融合画像）；④ **上下文四阶段压缩流水线** → 落地到 **长对话降级**（保护首尾、压缩中间工具结果，呼应模糊问题可解）。**明确不适用项**：RL 数据飞轮、自动 Skill 创建、47 工具集——本项目是固定领域 RAG，无训练基建、无需 agent 自写技能。

## 四、事项 B：检索生成的意图路由与链路升级

### B1 意图路由 LLM 主导化（3~4 天，核心）　✅ 已完成
新增统一路由节点，替换现有"正则为主"链路（正则降级为**零成本前置短路与兜底**，不再承担主决策）：

单次 LLM 调用（json_mode）输出：
```json
{
  "rewritten_query": "改写后用于检索的问句",
  "sub_queries": [{"q": "子问句", "domain": "tourism"}],
  "domains": ["tourism"],
  "source_policy": "kb | web | kb_then_web",
  "tools": ["none|weather|route|poi"],
  "is_plan": false,
  "need_clarify": false
}
```
设计要点：
- **改写与路由合一**：一次调用同时拿到改写问句与域标签，省一次 LLM 往返（也直接回应"模型转写问题发给服务"的诉求）。
- **数据源三档**：`kb`（库内事实）/`web`（时效、库外）/`kb_then_web`（库内为主、联网补时效）。
- **工具决策交给模型**：天气/路线/POI 由 LLM 判定，正则仅作极端情况下的兜底。
- **降级**：LLM 失败/超时 → 回落到现有正则链路（保证 40 题基线不崩）。**已拍板：采用单次调用 + 降级兜底**。

## 五、事项 C：旅行规划并行化（主人 2026-09-09 新增）

| C1 | **POI 事实核查逐条串行**（最大头） | `trip_planner_service.verify_plan`（400-475 行，node_verify_poi 调用）：`for day → for attr` 逐个 `_amap_text_search` | 3 日行程约 6~10 个 POI，每个一次高德 HTTP，串行约 10~20s+ | `ThreadPoolExecutor`（并发 4~6，尊重高德 QPS）+ 每 POI 独立超时与失败隔离 | 核查段 10~20s → 2~4s　✅ 已完成 |
