## 一、现状与问题

| 能力 | 现状 | 证据 | 问题 |
|---|---|---|---|
| 限流 | 仅**出站**限流：滑动窗口 + `time.sleep()` 阻塞等待 | `app/shared/utils/rate_limit_utils.py:12-40` | **阻塞式不可用于入站**——超配额时 sleep 会占住 worker，直接拖垮服务 |
| 入站 QPS 限流 | 无 | — | 公网暴露后无保护 |
| 鉴权 | 无。仅占位：空值/超长/注入关键词初筛 | `app/api/http/mobile_gateway.py:53-55` | 任何人可直接打穿到 query_server |
| 用户归属 | 占位：`SESSION_OWNER: session_id -> user_id` 内存字典 | `mobile_gateway.py:58` 附近 | 进程重启即丢，无法支撑长期记忆 |

> **核心原则：入站限流必须"拒绝式"（429 + Retry-After），出站限流才是"阻塞式"。两者不混用。**

## 二、身份链路（微信小程序）

```
小程序 wx.login()
   │  code
   ▼
网关 POST /auth/login {code}
   │  code + WX_APPID + WX_SECRET
   ▼
微信 jscode2session ──► openid (+ unionid/session_key)
   │
   ├─ 首次登录：生成 user_id(UUID)，写入 openid↔user_id 映射（MongoDB）
   │
   ▼
网关自签 JWT 返回 {access_token(2h), refresh_token(30d), user_id}
   │
   ▼
后续请求 Authorization: Bearer <access_token>
   └─ 网关校验 JWT → 解析 user_id → 写入 SESSION_OWNER[session_id]（接长期记忆）
```

### 存储设计（MongoDB，复用 `app/shared/clients/mongo_history_utils.py`）

集合 `users`：
```json
{
  "_id": "uuid-v4",
  "openid": "oXXXX",
  "unionid": "",
  "created_at": "ISO8601",
  "last_login": "ISO8601",
  "quota_plan": "free",
  "status": "active"
}
```
索引：`openid` 唯一索引；`last_login` 普通索引。

### JWT 载荷

```json
{"sub": "<user_id>", "openid": "oXXXX", "plan": "free", "iat": 0, "exp": 0, "typ": "access"}
```
- 算法 HS256，密钥 `JWT_SECRET`（≥32 字节随机串，仅存 .env，不进镜像）
- access 2h / refresh 30d；refresh 仅用于换 access，不携带业务权限

## 三、限流设计（拒绝式）

### 3.1 配额

| 维度 | 配额 | 超配额响应 |
|---|---|---|
| 单 `user_id` QPS | 2 req/s（生成类接口成本高） | `429` + `Retry-After: 1` |
| 单 `user_id` 日配额 | 200 次/天（按 `quota_plan` 可调） | `429` + 次日重置提示 |
| 单 IP QPS | 10 req/s（防刷，未登录请求也生效） | `429` |

### 3.2 存储选型：**待 T9 Redis**（主人已拍板）

- 计数结构：Redis `INCR` + `EXPIRE` 原子计数，`key = rl:{dim}:{id}:{window}`
- 跨进程共享：多副本网关部署时计数全局一致（单机内存令牌桶做不到）
- **依赖顺序**：T9（RedisBackend）→ T12（限流落地）。T8 本任务只出设计，不写单机占位版，避免返工。

### 3.3 与既有 `rate_limit_utils` 的关系

| 工具 | 方向 | 语义 | 位置 |
|---|---|---|---|
| `apply_api_rate_limit`（现有） | **出站** | 阻塞 sleep，保护第三方 API（高德/和风） | `utils/rate_limit_utils.py:12` |
| 新增入站限流器 | **入站** | 拒绝 429 | T12 新增，与上行不复用 |

## 四、接口契约

| 接口 | 方法 | 请求 | 响应 |
|---|---|---|---|
| `/auth/login` | POST | `{code}` | `{access_token, refresh_token, user_id, expires_in}` |
| `/auth/refresh` | POST | `{refresh_token}` | `{access_token, expires_in}` |
| `/auth/logout` | POST | Bearer | `{ok:true}`（加入 token 黑名单直至过期） |
| `/health` | GET | — | 已含 `role`/`config_ok`（T8 已落地） |

### 错误码

| HTTP | code | 场景 |
|---|---|---|
| 401 | `unauthorized` | 无 token / token 过期 / 签名错误 |
| 403 | `forbidden` | token 有效但用户 `status != active` |
| 429 | `rate_limited` | 命中任一维度配额，附 `Retry-After` |

## 五、分层防护执行顺序（与 T10 衔接）

```
请求 → ① 认证(JWT) → ② 限流(429) → ③ gateway_guard(脱敏/白名单/注入拦截, T10) → ④ 转发 query_server
```

- ① ② 属 T12；③ 的清单已由 T4 产出（`docs/分层防护清单.md`），T10 接入
- 未认证请求：仅允许 `/auth/*` 与 `/health`，其余 401

## 六、配置项（T12 落地时加入 `.env.example`）

| 键 | 说明 | 默认 |
|---|---|---|
| `AUTH_ENABLE` | 鉴权总开关（本地联调可关） | `false` |
| `JWT_SECRET` | HS256 密钥，≥32 字节 | 必填（开鉴权时） |
| `JWT_ACCESS_TTL` | access 有效期（秒） | `7200` |
| `JWT_REFRESH_TTL` | refresh 有效期（秒） | `2592000` |
| `WX_APPID` / `WX_SECRET` | 小程序凭据 | 必填（开鉴权时） |
| `RATE_LIMIT_ENABLE` | 入站限流开关 | `true` |
| `RATE_LIMIT_USER_QPS` | 单用户 QPS | `2` |
| `RATE_LIMIT_USER_DAILY` | 单用户日配额 | `200` |
| `RATE_LIMIT_IP_QPS` | 单 IP QPS | `10` |
| `RATE_LIMIT_REDIS_URL` | 计数 Redis（依赖 T9） | 复用 `CACHE_REDIS_URL` |
