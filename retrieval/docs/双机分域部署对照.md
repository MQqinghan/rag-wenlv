# 双机分域部署对照（Import 域 / Retrieval 域）

> 2026-09-10 | 主人拍板方案甲：不物理拆目录，双机分域复用 T8 进程级切片（`APP_ROLE`）。
> 本文件是 `docs/部署清单.md` 在「一台机器跑导入、一台（手机）跑查询」拓扑下的**补充**；通用角色/配置/启动/检查单见主清单。

---

## 一、为什么不需要物理拆目录

- T8 实测：导入端 ↔ 查询端**零交叉引用**，部署切片的本质是**进程级隔离**而非文件级隔离。
- 双机分域靠 `APP_ROLE` 进程切片即可：同一份代码库，每台机器只设自己的 `APP_ROLE`，启动时 `startup_role_check()` 按角色加载必需配置并自检。物理拆目录（乙/丙）对"分机跑"**无额外技术收益**，只增 import 重写 + 共享层归属风险。
- 呼应主人「Import / Retrieval 两文件夹」的命名意图：两个**逻辑域**通过 `APP_ROLE` 在进程层面隔离，无需物理移动文件。

---

## 二、双机拓扑

```
机器 A（导入域 / Import）                机器 B（查询域 / Retrieval，手机可达）
┌──────────────────────────┐          ┌──────────────────────────────────┐
│ APP_ROLE=import          │          │ APP_ROLE=query                   │
│ import_server   :8000    │          │ query_server    :8001            │
│ （写 Milvus / MinIO）    │          │ mobile_gateway  :8002 （可选 BFF）│
└────────────┬─────────────┘          └────────────────┬─────────────────┘
             │                                          │
             └──── 共享基础设施：Milvus / Mongo / MinIO（共用一套最稳，见第四节） ────┘

手机 / 小程序 → 机器 B 的 gateway(8002)（或直连 query 8001）；导入在机器 A 独立跑。
```

## 三、域名 ↔ 角色 ↔ 端口 ↔ 机器 对照表

| 逻辑域 | `APP_ROLE` | 入口 / 端口 | 部署机器 | 必需配置 | 加载模型 |
|---|---|---|---|---|---|
| **Import（导入）** | `import` | `import_server` / 8000 | 机器 A | `MILVUS_URL`、`MINIO_ENDPOINT`、`MINIO_ACCESS_KEY`、`MINIO_SECRET_KEY`、`MINIO_BUCKET_NAME`、`IMPORT_EGRESS_MODE` | Embedding |
| **Retrieval（检索生成）** | `query` | `query_server` / 8001 | 机器 B | `MILVUS_URL`、`OPENAI_API_KEY`、`OPENAI_BASE_URL`、`MONGO_URL` | Embedding + Reranker |
| 网关（可选） | `gateway` | `mobile_gateway` / 8002 | 机器 B | 无（均有代码内默认值；T12 鉴权后补 `WX_APPID`/`WX_SECRET`/`JWT_SECRET`） | 否（纯转发） |

> 命名说明：检索生成域实际还含意图路由 / 行程规划 / 答案生成，本质是"问答服务"，`Retrieval` 为与主人原词对齐的简称；若后续想要更贴切命名可改为 `Serve` / `Query`，仅需同步改文档，不影响代码。

## 四、跨机部署编排

- **同一份代码 + 分段 `.env`**（T2 已做「共享底座 / IMPORT / QUERY」三段）：
  - 机器 A 的 `.env` 只需填 **共享底座 + IMPORT 段**；
  - 机器 B 的 `.env` 只需填 **共享底座 + QUERY 段**。
- **compose 分机**：
  - 机器 A 只起 `import`：`docker compose up -d import`（或单独 `docker build -f Dockerfile.import`）；
  - 机器 B 起 `query`（+`gateway`）：`docker compose up -d query gateway`。
- **共享基础设施**：导入写、查询读，故 Milvus / Mongo / MinIO **共用一套实例最稳**——两台机器 `.env` 的 `MILVUS_URL` / `MONGO_URL` / `MINIO_ENDPOINT` 指向同一地址；若各机自带需注意数据写入一致性（不推荐）。
- 容器默认 `ROLE_STRICT_CHECK=true`，缺必需配置 **fail-fast 阻断启动**，不会带病运行。

## 五、启动自检清单（双机版）

**机器 A（导入域）**
- [ ] `APP_ROLE=import`，`ROLE_STRICT_CHECK=true`
- [ ] `.env` 共享底座 + IMPORT 段齐全（`MILVUS_URL` / `MINIO_*` / `IMPORT_EGRESS_MODE`）
- [ ] 挂载 `./models`（Embedding）、`./logs`（外发审计）、`./data`（导入临时）
- [ ] 确认 `IMPORT_EGRESS_MODE` 档位（off / mask / full，见 `docs/分层防护清单.md`）
- [ ] `GET /health` → `{"role":"import","config_ok":true,"missing_required":[]}`

**机器 B（查询域）**
- [ ] `APP_ROLE=query`，`ROLE_STRICT_CHECK=true`
- [ ] `.env` 共享底座 + QUERY 段齐全（`MILVUS_URL` / `OPENAI_*` / `MONGO_URL`）；推荐 `QWEATHER_API_KEY` / `AMAP_API_KEY` / `MCP_DASHSCOPE_BASE_URL`（缺则天气 / 路线 / 联网检索降级）
- [ ] 挂载 `./models`（Embedding + Reranker）、`./logs`
- [ ] 若起 `gateway`：`QUERY_HOST` 指向本机 `query`(8001)
- [ ] `GET /health` → `{"role":"query","config_ok":true,"missing_required":[]}`

## 六、与目录结构的关系（回应「拆成两个文件夹」）

- 代码维持单 `app/` 包；两个逻辑域通过 `APP_ROLE` 在进程层面隔离，**无需物理移动文件**。
- 仅在 `docs/分层回归策略.md` / 本文件做**逻辑归属标注**（import 端入口 `import_server.py`、query 端入口 `query_server.py`）。
- **未来若需仓库级 / 打包级隔离**（分别给两台机器发不同的包），再评估方案乙（`app/import_side` + `app/retrieval_side`）或丙（物理两顶层包 `Import/` + `Retrieval/`），且须先把 `docs/共享层归属清单.md` 的共享层 27 模块归属敲定再动手。**当前不执行物理拆分。**
