# 检索生成模块 · 节点步骤分解（合并版）

> 所属图①：统一查询图 unified_query_app（app/process/unified_query/agent/main_graph.py，15 个节点，生产主链路，文旅/闲聊意图路由 + 规划类增强）
> 节点执行顺序（统一图）：node_intent_route → route_by_domain 分发（chitchat 内按 is_datetime_query/is_confusion 细分）→ node_attraction_confirm（文旅）→ 四路并行检索 [node_search_embedding | node_search_embedding_hyde | node_keyword_search | node_web_search_mcp]（规划类问题 is_plan=True 时追加并行 [node_tool_weather | node_tool_route]）→ node_rrf → node_rerank → 按 domain/is_plan 进入 node_answer_output / node_itinerary_generate / node_chitchat_answer；纯时间/日期询问直接走 node_datetime_answer（系统时钟直答），困惑澄清输入（"？"等）直接走 node_clarify（不联网、不走检索）；指代不明咨询句（"那边天气怎么样"类，2026-09-04 P3）由 route_by_domain 直走 node_chitchat_answer 的确定性澄清反问（跳过联网搜索 node_web_search_mcp）
> 关键口径：联网结果不参与 RRF 融合（仅作同步屏障，在 rerank 阶段合并）；RRF 为三路融合（向量 + 多改写 + BM25 关键词），k=60，输出 Top5；重排模型 bge-reranker-large（512 token 上限，默认零 LLM 抽取式压缩）
> 本文档由「docs 步骤分解」下的查询节点文档按节点执行顺序合并而成，所有 文件:行号 引用均经代码实测核对。

## 一、node_intent_route（意图路由，规划识别 + 三层判定 + 指代不明拦截）

> 节点位置：`app/process/unified_query/agent/nodes/node_intent_route.py`
> 所属图：统一查询图 unified_query_app（app/process/unified_query/agent/main_graph.py）
> 调用服务：`app/rag/common/intent_route_service.py`

### 1. 导入与配置
引入 `sys`（获取当前函数名）、`DOMAIN_CHITCHAT`/`classify_intent`（意图路由服务）、`node_log`（节点日志装饰器）、`add_done_task`/`add_running_task`（任务状态上报）。
- 导入：node_intent_route.py:5-9
- 装饰器 `@node_log("node_intent_route")`：node_intent_route.py:12
- 意图域常量定义在 service 侧：`DOMAIN_TOURISM="tourism"`、`DOMAIN_CHITCHAT="chitchat"`（intent_route_service.py:21-23）
- 缓存与句式：追问最大长度 `_FOLLOWUP_MAX_LEN=20`（intent_route_service.py:46）；追问句式 `_FOLLOWUP_PATTERN`、知识型句式 `_KNOWLEDGE_QUERY_PATTERN`（intent_route_service.py:47-57）；**域外产品词 `_OFF_DOMAIN_PRODUCT_PATTERN`（2026-09-04 P2 新增：手机/数码/3C 产品词，在知识型句式兜底之前拦截归闲聊走联网，修"华为P60拍照怎么样"误入文旅域）**；规划类句式 `_PLAN_QUERY_PATTERN`（intent_route_service.py:61-63，匹配「规划/帮我安排/行程安排/路线安排/旅游计划」等）

### 2. 节点入口函数
`node_intent_route(state)` 是统一查询图入口节点（main_graph.py:55、75）：先 `add_running_task` 标记任务开始，再调用 `classify_intent(state)` 得到 domain 写入 `state["domain"]`，随后 `add_done_task` 标记完成并返回 state。
- 输入：`state['original_query']`、`state['session_id']`、`state['history_text']`（LLM 兜底使用）
- 输出：`state['domain']`，供统一图 `route_by_domain` 条件路由分发（main_graph.py:79-95）
- 关键行为：当 domain 为 `chitchat` 时预填 `state["rewritten_query"] = original_query`（node_intent_route.py:24-25），因闲聊分支不经过主体改写节点，而联网搜索节点要求 rewritten_query 非空。

### 3. Service 总入口
`classify_intent(state)` 是意图路由服务总入口，按「规划类标记（第零层）→ 追问继承 → 关键词规则 → LLM 兜底（带缓存）」顺序完成二分类判断（intent_route_service.py:236-274）。

### 3.5 步骤 0: 规划类标记（第零层）
`_PLAN_QUERY_PATTERN.search(query)` 在一切分类前先做零成本正则命中（intent_route_service.py:251-254）：命中即写 `state["is_plan"] = True`（只标记、不改域，供后续规划分支消费），并记录日志。之所以前置：规划类问句常不含文旅关键词（如「我明天想去九寨沟，帮我规划一下」），走 LLM 兜底易被误判闲聊；且短追问「那帮我规划一下」也能在追问继承前被捕获。规划类问句本质是出行安排，故在规则层（步骤 3）同时显式归 `tourism`（intent_route_service.py:151-153）。

### 5. 步骤 2: 追问继承（第一层）
`inherit_domain_if_followup(query, session_id)` 对短追问（长度 ≤ `_FOLLOWUP_MAX_LEN=20` 且匹配 `_FOLLOWUP_PATTERN` 开头/结尾）直接复用上一轮业务域（intent_route_service.py:198-233）。通过 `history_repository.list_recent(session_id, limit=3)` 读取上轮 domain，**仅继承 tourism**（闲聊后不继承，避免挡掉检索）（intent_route_service.py:227-232）。

### 5.5 步骤 2.5: 指代不明咨询句拦截（2026-09-04 P3 新增）
`_DEIXIS_CONSULT_PATTERN.match(query)` 对"那边/那里/这边/这里/当地/此地"开头的句子零成本命中（intent_route_service.py:396-404）：置 `state["is_unresolved_deixis"] = True`（同时清 `is_confusion`/`is_datetime_query` 防串扰）后返回 `DOMAIN_CHITCHAT`。只放追问继承之后——有可继承历史时"那边"有先行词，已在上层正常继承，走不到这里。下游两处消费该标记：`route_by_domain` 据此让指代句**跳过联网搜索**直走 node_chitchat_answer（main_graph.py）；`generate_chitchat_answer` 早期分支返回确定性澄清反问"您说的「那边」我还不清楚具体指哪里——请补充一下具体地点（城市或景区名），我再帮您查询。"（零 LLM、不联网，修 cl-002 指代句被闲聊模板编造"阳光明媚"）。教训：LangGraph 条件边路由函数新增返回值 `node_chitchat_answer` 必须同步登记进 `add_conditional_edges` 的路径映射 dict，否则 KeyError 图执行异常。

### 6. 步骤 3: 关键词规则匹配（第二层）
`match_by_rule(query)` 将查询转小写后，按 **chitchat → tourism** 顺序遍历关键词表，任一命中立即返回对应域；三组均未命中时检查 `_KNOWLEDGE_QUERY_PATTERN`（"什么是/为什么/怎么…"），命中则兜底归 `tourism`（检索优先，避免知识型问句被误判闲聊而走联网）（intent_route_service.py:131-153）。**域外产品兜底标记（2026-09-04 P3）**：规则命中 chitchat 且同时命中 `_OFF_DOMAIN_PRODUCT_PATTERN` 时置 `state["is_off_domain_product"] = True`，供闲聊答案末尾追加"以官方发布为准"限定语，修 judge 对无出处参数断言判定抖动（neg-002）。关键词表见 `_CHITCHAT_KEYWORDS`/`_TOURISM_KEYWORDS`（intent_route_service.py:27-43）。

### 7. 步骤 4: LLM 兜底分类（第三层）
`classify_by_llm(query, history_text)` 在前几层均未命中时启用，经 `cached_invoke(namespace="intent_route", ...)` 走进程内 LLM 缓存（同输入命中时零延迟）（intent_route_service.py:180-195）。实际调用 `_call_intent_model`：用 `llm_provider.chat(json_mode=True)` 加载 `tourism/intent_route` prompt，经 `SystemMessage` + `HumanMessage` + `JsonOutputParser` 解析 domain（intent_route_service.py:156-177）。**反闲聊覆盖**：当 LLM 判 chitchat 但 query 命中知识型句式时，推翻为 tourism（intent_route_service.py:171-174）。返回域非法/异常时默认走 `DOMAIN_TOURISM`。

### 8. 单元测试
该节点文件未内置单元测试。可在统一查询图 `main_graph.py` 中验证：其 `__main__` 冒烟测试（main_graph.py:206-222）以 `original_query="你好"` 执行 `unified_query_app.stream(...)`，观察执行序列应命中 chitchat 分支（node_intent_route → node_web_search_mcp → node_chitchat_answer），并检查 `state["domain"]` 的二分类结果与 `rewritten_query` 预填。原始查询为空时默认返回 tourism（intent_route_service.py:244-246）。

## 二、node_attraction_confirm（文旅：主体确认与问题改写）

> 节点位置：`app/process/unified_query/agent/nodes/node_attraction_confirm.py`
> 所属图：统一查询图 unified_query_app（app/process/unified_query/agent/main_graph.py）
> 调用服务：`app/rag/tourism_query/attraction_confirm_service.py`

### 1. 导入与配置
引入 `sys`、`confirm_attractions`（主体确认服务）、`node_log`、`add_done_task`/`add_running_task`。
- 导入：node_attraction_confirm.py:5-9
- 配置常量（service 侧）：`QUERY_HISTORY_LIMIT=10`、`ENTITY_CONFIRM_THRESHOLD=0.65`、`ENTITY_CANDIDATE_THRESHOLD=0.50`、`ENTITY_OPTIONS_TOPK=2`（attraction_confirm_service.py:17-20）
- 主体库为 `tourism_entity`；无确认主体时**不生成澄清话术**，item_names 为空直接走全库检索兜底（attraction_confirm_service.py:1-4）。

### 2. 节点入口函数
`node_attraction_confirm(state)` 是 LangGraph 节点入口：`add_running_task` 标记开始 → 调用 `confirm_attractions(state)` 更新 state → `add_done_task` 标记完成并返回。
- 输入：`state['original_query']`、`state['session_id']`
- 输出：更新 `state['item_names']` 与 `state['rewritten_query']`
- 图内位置：由 `route_by_domain` 在 domain=tourism 时指向该节点（main_graph.py:79-95）；执行后经 `after_attraction_confirm` 分发——`state.answer` 已存在则直出 `node_answer_output_tourism`，否则四路并行检索，**且当 `state.is_plan=True` 时额外并行追加 `node_tool_weather` 与 `node_tool_route` 两个规划类工具节点**（main_graph.py:124-145、131-142）。

### 3. Service 总入口
`confirm_attractions(state)` 是主流程总入口，串联「校验 → 读历史 → LLM 改写+抽取 → 主体库候选 → 高置信确认 → 写回 → 落库」（attraction_confirm_service.py:165-188）。

### 4. 步骤 1: 校验查询身份
`validate_query_identity(state)` 检查 `original_query` 与 `session_id` 均非空，缺失时抛 `ValueError`（attraction_confirm_service.py:23-31）。

### 5. 步骤 2: 加载会话历史
`load_history(session_id)` 调用 `history_repository.list_recent(session_id, limit=10)` 读取最近 10 条历史消息，供改写 prompt 拼接上下文（attraction_confirm_service.py:34-37）。

### 6. 步骤 3: 改写问题并抽取主体
`rewrite_query_and_extract_attractions(history_messages, original_query)` 一次 LLM 调用同时完成：①问题改写为 `rewritten_query`；②抽取主体列表 `attractions`（景点名/文化主题）。使用 `llm_provider.chat(json_mode=True)` + `tourism/rewritten_query_and_attractions` prompt + `JsonOutputParser`，并经 `cached_invoke(namespace="tourism_query_rewrite", ...)` 缓存（attraction_confirm_service.py:40-76）。字段缺失时做兜底：rewritten_query 回退为原始问题、attractions 置为空列表。

### 7. 步骤 4: 主体库候选检索
`search_entity_candidates(attractions)` 将每个抽取主体用 `llm_provider.embed_documents` 向量化（dense+sparse），构造请求后对 `milvus_gateway.tourism_entity_collection` 执行 `hybrid_search`（权重 0.5/0.5，norm_score=True，输出 item_name），返回「主体名 → 候选列表」映射（attraction_confirm_service.py:79-122）。向量化失败或集合未创建时记警告并置空，不阻断流程。

### 8. 步骤 5: 高置信主体确认
`select_confirmed_entities(vector_dict)` 对每个主体的候选按 score 降序，仅保留 `score >= 0.65`（ENTITY_CONFIRM_THRESHOLD）的候选并取最高分项作为确认主体；**无高置信主体时不生成澄清话术**，直接留空（attraction_confirm_service.py:125-137）。

### 9. 步骤 6: 写回查询状态
`apply_attraction_result(state, confirmed, rewritten_query)` 将 `confirmed` 写入 `state["item_names"]`、改写问题写入 `state["rewritten_query"]`，并清除可能残留的 `state["answer"]`（attraction_confirm_service.py:140-149）。

### 10. 步骤 7: 用户消息落库
`save_user_message(state)` 通过 `history_repository.save_message` 以 role=user 保存原始问题、改写结果与确认主体（含 domain 字段）（attraction_confirm_service.py:152-162）。

### 11. 单元测试
该节点文件未内置单元测试。可在统一查询图 `main_graph.py` 中验证：以 tourism 域问题（如 `original_query="云南泼水节旅游攻略"`）执行 `unified_query_app.stream(state, stream_mode="updates")`，观察 `node_attraction_confirm` 执行后日志「文旅主体确认：抽取[...]，确认[...]」（attraction_confirm_service.py:182-184），并核对 state 中 `item_names` 是否为空（空则后续检索走全库兜底）。

## 三、node_search_embedding（文旅：向量混合检索）

> 节点位置：`app/process/unified_query/agent/nodes/node_search_embedding.py`
> 所属图：统一查询图 unified_query_app（app/process/unified_query/agent/main_graph.py）
> 调用服务：`app/rag/tourism_query/search_embedding_service.py`

### 1. 导入与配置
引入 `sys`、`search_embedding`（向量检索服务）、`node_log`、`add_done_task`/`add_running_task`。
- 导入：node_search_embedding.py:5-9
- 配置常量（service 侧）：`RETRIEVAL_DEFAULT_LIMIT=5`、`RETRIEVAL_RANKER_WEIGHTS=(0.9, 0.1)`（search_embedding_service.py:10-11）
- 模型：BGE-M3 稠密 + 稀疏双向量检索（向量维度为模型属性，未在 service 中以常量显式声明）；支持「无主体全库检索」——item_names 为空时不带过滤条件（search_embedding_service.py:1-4）。

### 2. 节点入口函数
`node_search_embedding(state)` 是 LangGraph 节点入口：`add_running_task` 标记开始 → 调用 `search_embedding(state)` 得到结果列表 → `add_done_task` 标记完成 → 返回 `{"embedding_chunks": result}` 写入 state。
- 输入：`state['rewritten_query']`、`state['item_names']`
- 输出：`state['embedding_chunks']`，供 node_rrf 融合
- 图内位置：文旅四路并行检索之一（注册名 `node_search_embedding_tourism`，main_graph.py:64）；经静态边 `node_search_embedding_tourism -> node_rrf` 汇聚（main_graph.py:169）。

### 3. Service 总入口
`search_embedding(state)` 是总入口，负责校验改写问题、读取 item_names，并委托 `search_tourism_chunks` 执行混合检索（search_embedding_service.py:14-30）。

### 4. 步骤 1: 校验改写问题
从 state 取 `rewritten_query`（兜底 `original_query`），为空时抛 `ValueError` 中断业务；同时读取 `item_names`（缺省空列表）（search_embedding_service.py:25-29）。

### 5. 步骤 2: 嵌入查询向量
`search_tourism_chunks` 调用 `llm_provider.embed_documents([rewritten_query])`，取出 dense（稠密）与 sparse（稀疏）两路向量，作为混合检索的查询表示（search_embedding_service.py:132）。

### 6. 步骤 3: 构建主体过滤表达式
`build_entity_expr(item_names)` 生成 Milvus 过滤表达式 `item_name in [...]`；`search_tourism_chunks_by_vector` 中 **item_names 为空时 expr 置为 None**，即执行全库检索兜底（search_embedding_service.py:33-36、88-92）。

### 7. 步骤 4: 混合检索 tourism_chunks
构造 `create_requests(dense, sparse, expr, limit=5)` 请求，对 `milvus_gateway.tourism_chunks_collection` 执行 `hybrid_search`（ranker_weights=(0.9,0.1)，norm_score=True），输出 chunk_id/item_name/content/title/region/cultural_theme 等文旅字段（search_embedding_service.py:94-110）。

### 8. 步骤 5: 归一化检索结果
`normalize_retrieved_chunk(chunk)` 将每条 Milvus 原始结果映射为查询链统一文档结构，携带 `chunk_id`、`item_name`、`title`、`content`、`score`、`type="milvus"`、`url=None` 等字段，供 RRF/重排/答案生成消费（search_embedding_service.py:39-62）。

### 9. 单元测试
该节点文件未内置单元测试。可在统一查询图 `main_graph.py` 中验证：以 tourism 域问题执行 `unified_query_app.stream(...)`，观察日志出现「文旅定向检索，过滤主体：[...]」或「文旅全库检索（无确认主体，纯文化问题兜底）」（search_embedding_service.py:90-92），并在流式更新中确认 `node_search_embedding_tourism` 产出非空 `embedding_chunks`。

## 四、node_search_embedding_hyde（文旅：多改写增强检索）

> 节点位置：`app/process/unified_query/agent/nodes/node_search_embedding_hyde.py`
> 所属图：统一查询图 unified_query_app（app/process/unified_query/agent/main_graph.py）
> 调用服务：`app/rag/tourism_query/search_embedding_hyde_service.py`（内部复用 `search_embedding_service.search_tourism_chunks_by_vector` 与 `common/multi_query_service`）

### 1. 导入与配置
引入 `sys`、`search_embedding_hyde`（多改写检索服务）、`node_log`、`add_done_task`/`add_running_task`。
- 导入：node_search_embedding_hyde.py:5-9
- 多改写服务导入：`MULTI_QUERY_ENABLE`/`build_multi_queries`/`generate_query_variants`/`retrieve_multi_queries`（multi_query_service.py:11-20）、`RETRIEVAL_DEFAULT_LIMIT`/`search_tourism_chunks_by_vector`（search_embedding_service.py:14-20）
- 多改写配置（common/multi_query_service.py:25-33）：`MULTI_QUERY_ENABLE`（默认 True）、`MULTI_QUERY_MAX_REWRITES=2`、`MULTI_QUERY_WORKERS=4`、`MULTI_QUERY_MAX_LENGTH=100`、`HYDE_ANSWER_MAX_LENGTH=300`
- 提示词与系统角色：`tourism/multi_query`、`_MULTI_QUERY_SYSTEM`（search_embedding_hyde_service.py:24-25）

### 2. 节点入口函数
`node_search_embedding_hyde(state)` 是 LangGraph 节点入口：`add_running_task` 标记开始 → 调用 `search_embedding_hyde(state)` 得到多改写检索结果 → `add_done_task` 标记完成 → 返回 `{"hyde_embedding_chunks": result}`。
- 输入：`state['rewritten_query']`、`state['item_names']`
- 输出：`state['hyde_embedding_chunks']`，供 node_rrf 融合
- 图内位置：文旅四路并行检索之一（注册名 `node_search_embedding_hyde_tourism`，main_graph.py:65）；经静态边 `node_search_embedding_hyde_tourism -> node_rrf` 汇聚（main_graph.py:170）。

### 3. Service 总入口
`search_embedding_hyde(state)` 是总入口：校验改写问题后，对短查询（<15 字）或已确认主体的查询**跳过扩展直接返回空列表**（RRF 仍可用其他路结果融合），否则委托 `search_chunks_with_multi_query` 完成多改写检索（search_embedding_hyde_service.py:28-47）。

### 4. 步骤 1: 校验与跳过条件
从 state 取 `rewritten_query`（兜底 `original_query`），为空时抛 `ValueError`（search_embedding_hyde_service.py:40-42）。读取 `item_names`；当 `len(rewritten_query) < 15` 或 `item_names` 非空时直接返回 `[]`，避免噪声与不必要的约 2s 扩展耗时（search_embedding_hyde_service.py:43-46）。

### 5. 步骤 2: 一次 LLM 产出多路改写 + HyDE 假设答案
`generate_query_variants(prompt_name="tourism/multi_query", rewritten_query, system_message)` 一次 LLM 调用（json_mode + JsonOutputParser）同时产出 `rewrites`（最多 `MULTI_QUERY_MAX_REWRITES=2` 条视角改写）与 `hyde_answer`（一段 HyDE 假设答案，截断到 300 字）；每条改写经 `clean_rewrite_text` 清洗序号前缀/引号/超长（multi_query_service.py:39-104）。

### 6. 步骤 3: 拼装多路查询
`build_multi_queries(rewritten_query, variants, enable_multi=MULTI_QUERY_ENABLE)` 将视角改写与「原问题 + 假设答案」拼接的 HyDE 查询合并；启用多改写时加入 rewrites，始终加入 HyDE 拼接查询；去重并排除与原始 query 完全相同的项（multi_query_service.py:107-134）。

### 7. 步骤 4: 批量编码 + 并发检索 + 去重合并
`retrieve_multi_queries` 调用 `llm_provider.embed_documents(queries)` **一次性批量编码**（规避 BGE-M3 全局锁串行），再经线程池（max_workers=`MULTI_QUERY_WORKERS`）并发调用 `search_tourism_chunks_by_vector` 逐路检索，按 `chunk_id` 去重合并（首次命中优先）（multi_query_service.py:137-185）。
- 复用普通检索：`search_tourism_chunks_by_vector(dense, sparse, item_names, limit)` 支持空 item_names 全库兜底（search_embedding_service.py:65-111）。

### 8. 单元测试
该节点文件未内置单元测试。可在统一查询图 `main_graph.py` 中验证：以 tourism 域"长且开放"的问题（≥15 字、无明确主体）执行 `unified_query_app.stream(...)`，确认 `node_search_embedding_hyde_tourism` 执行后流式更新中出现非空 `hyde_embedding_chunks`，并与普通路/关键词路一起进入 node_rrf 融合（日志可见「多改写检索完成：N 路查询，去重后 M 条结果」，multi_query_service.py:184）。短查询（<15 字）则该路为空，验证跳过条件。

## 七、node_rrf（三路倒数排名融合）

> 节点位置：`app/process/unified_query/agent/nodes/node_rrf.py`
> 所属图：统一查询图 unified_query_app（app/process/unified_query/agent/main_graph.py）
> 调用服务：`app/rag/common/rrf_service.py`（算法为共享实现）

### 1. 导入与配置
引入 `sys`、`fuse_by_rrf`（RRF 融合服务）、`node_log`、`add_done_task`/`add_running_task`。
- 导入：node_rrf.py:5-9
- 配置常量（service 侧）：`RRF_K=60`（平滑系数）、`RRF_TOP=5`（最终返回条数）（rrf_service.py:9-11）

### 2. 节点入口函数
`node_rrf(state)` 是 LangGraph 节点入口：`add_running_task` 标记开始 → 调用 `fuse_by_rrf(state)` → `add_done_task` → 返回 `{"rrf_chunks": rrf_chunks}`。
- 输入：`state['embedding_chunks']`、`state['hyde_embedding_chunks']`、`state['keyword_chunks']`
- 输出：`state['rrf_chunks']`，供 node_rerank 精排
- 图内位置：作为多路并行检索的**同步屏障**，文旅各检索边均汇聚到此（main_graph.py:166-171），随后 `node_rrf -> node_rerank`（main_graph.py:172）。联网检索 `node_web_search_mcp` 也有静态边汇入（main_graph.py:169 区域）作为同步屏障；web 结果不参与 RRF 分数融合，仅在 rerank 阶段合并。

### 3. Service 总入口
`fuse_by_rrf(state)` 是总入口，按「校验输入 → 构造加权参数 → 执行 RRF 核心算法」三步完成**本地三路**结果的倒数排名融合（rrf_service.py:14-38）。只处理本地知识库召回（向量 + 多改写 + 关键词），不参与外网网页合并（rrf_service.py:1-4）。

### 4. 步骤 1: 校验三路输入
`validate_rrf_inputs(state)` 取出 `embedding_chunks`、`hyde_embedding_chunks`、`keyword_chunks`；允许单路有结果（多改写/关键词均可能因开关或跳过条件返回空），但**三路皆空时抛 `ValueError`** 中断融合（rrf_service.py:41-63）。

### 5. 步骤 2: 构造融合参数
组装 `param_list = [(embedding_chunks, 1.0), (hyde_embedding_chunks, 1.0), (keyword_chunks, 1.0)]`，普通向量路/多改写路/BM25 关键词路默认权重均为 1.0（RRF 只看排名不看原始分数，权重相等即公平投票）（rrf_service.py:31-35）。

### 6. 步骤 3: 核心 RRF 分数累加
`reciprocal_rank_fusion` 遍历每一路结果，对每个片段以 `chunk_id` 为键累加 `1/(k+rank) * weight` 融合分（k=RRF_K=60），并用 `entity_dict.setdefault` 保留片段原文信息（只存一次避免覆盖）；无 chunk_id 的片段跳过（rrf_service.py:66-109）。

### 7. 步骤 4: 排序并取 Top N
将融合分写入各文档 `score` 字段，按分数降序排序，截取前 `top=5` 条作为最终融合结果返回，并记录输入路数/输出条数日志（rrf_service.py:104-117）。

### 8. 单元测试
该节点文件未内置单元测试。可在统一查询图 `main_graph.py` 中验证：以 tourism 域问题执行 `unified_query_app.stream(...)`，在普通+多改写+关键词三路检索完成后观察 `node_rrf` 输出；日志应出现「RRF融合完成,输入路数:3,输出条数:N」（rrf_service.py:116），并核对 `rrf_chunks` 按融合分数降序。

### 2. 节点入口函数
`node_rerank(state)` 是 LangGraph 节点入口：`add_running_task` 标记开始 → 调用 `rerank_documents(state)` → `add_done_task` → 返回 `{"reranked_docs": reranked_docs}`。
- 输入：`state['rrf_chunks']`、`state['web_search_docs']`、`state['rewritten_query']`
- 输出：`state['reranked_docs']`，供按 domain 分发的答案输出节点
- 图内位置：文旅汇聚后的共享精排节点（main_graph.py:71）；重排后经 `after_rerank` 按 domain/is_plan 分发——规划类文旅问题（`domain=tourism` 且 `is_plan`）进 `node_itinerary_generate`，其余按 domain 进入对应答案输出节点（main_graph.py:176-192）；闲聊域不进此节点（由 after_web_search 直送 chitchat_answer，main_graph.py:149-162）。

### 3. Service 总入口
`rerank_documents(state)` 是主流程总入口：校验输入 → 合并本地+网页 → 模型打分排序 → 动态截断（rerank_service.py:49-69）。这是查询链中第一次让本地与网页候选进入同一评分体系的**跨来源统一精排**（rerank_service.py:1-4）。

### 4. 步骤 1: 校验输入
`validate_rerank_inputs(state)` 取出 `rrf_chunks` 与 `web_search_docs`；允许单路为空，但**两路皆空时抛 `ValueError`**（rerank_service.py:72-92）。

### 5. 步骤 2: 统一格式合并两路候选
`merge_rrf_and_web` 将本地结果统一为 `{title, text=content, url=None, type=milvus, score}`，网页结果统一为 `{title, text=snippet, url, type=web, score=0}`，合并为一个候选列表（rerank_service.py:95-131）。

### 6. 步骤 3: 构建问题-文本对（超长分治压缩）
`build_question_pairs(question, final_chunk_list, reranker)` 用重排模型自带 tokenizer 估算总长（approx query_tokens + 4 特殊 token），反推单条字符上限 `limit`（rerank_service.py:283-348）。先用 `collect_oversized_items` 按字符粗筛超长项（rerank_service.py:254-280），再按来源分治：
- 网页类（type=web）：`truncate_text_for_rerank` 硬截断（rerank_service.py:239-251）；
- 本地类（type=milvus）：`condense_text_for_rerank` 句子级抽取式压缩（按与问题词汇重叠度挑关键句并保序，rerank_service.py:180-236，依赖 `split_sentences` 134-146、`extract_terms` 149-177）；
- 仅当 `RERANK_LLM_REFINE_ENABLE=1` 时调用 `summarize_long_rerank_text`（common/rerank_text_refine prompt，rerank_service.py:351-378），多条时线程池并行（rerank_service.py:315-326）。

### 7. 步骤 4: 重排模型打分并排序
`score_and_sort_chunks` 取 `llm_provider.reranker_model()`，对全部问答对调用 `compute_score(question_pairs, normalize=True)` 归一化打分，将分数 round 到 4 位写回文档并按分数降序排序（rerank_service.py:381-411）。

### 8. 步骤 5: 分数断崖动态截断
`dynamic_topk` 默认取 `min(10, 总数)` 条，从第 1 条起向后扫描相邻分数差：当绝对差 `> RERANK_GAP_ABS` 或比例差 `> RERANK_GAP_RATIO` 时判定为分数断崖，在该位置截断，返回最终精排候选列表（rerank_service.py:414-446）。

### 9. 单元测试
该节点文件未内置单元测试。可在统一查询图 `main_graph.py` 中验证：以 tourism 域问题执行 `unified_query_app.stream(...)`，观察 `node_rerank` 输出非空 `reranked_docs`；日志可见「两路数据统一格式完成」与「超长候选筛出 M/N 条」；构造本地/网页均无结果的 state 会触发「rerank 重排失败」异常验证输入校验（rerank_service.py:88-90）。

> 所属图：统一查询图 unified_query_app（app/process/unified_query/agent/main_graph.py）
> 调用服务：`app/rag/tourism_query/answer_output_service.py`

### 1. 导入与配置
引入 `sys`、`generate_answer`（答案生成服务）、`node_log`、`add_done_task`/`add_running_task`。
- 导入：node_answer_output.py:5-9
- 服务侧依赖：`re`/`time`、`llm_provider`、`history_repository`、`build_history_text`、`tourism/answer_out` prompt、`SSEEvent`/`push_to_session`、`set_task_result`、`normalize_answer_text`（answer_output_service.py:5-15）
- 引用标记正则 `_CITATION_PATTERN = (?:\s*【(?:第\d+块|\d+)】)+`（流式 delta 级剥离，answer_output_service.py:18）
- 使用 `tourism/answer_out` 模板；item_names 语义为景点名/文化主题（answer_output_service.py:1-3）。
- **代办类前置声明 `_BOOKING_DISCLAIMER`（2026-09-04 P3）**：`_BOOKING_INTENT_PATTERN`（"帮我订/替我订/代订/代办"等）命中时，`final_answer` 在流式最先推该 delta、非流式拼在答案出处分节之前："先说明：我无法代为预订酒店、机票或门票，以下信息仅供您参考，实际预订请通过官方或正规平台办理。"（修 cl-003 能力边界无声明）。

### 2. 节点入口函数
`node_answer_output(state)` 是 LangGraph 节点入口：`add_running_task` 标记开始 → 调用 `generate_answer(state)` 就地更新 state → `add_done_task` → 返回 state。
- 输入：`state['reranked_docs']`、`state['rewritten_query']`、`state['item_names']`、`state['history']`
- 输出：更新 `state['answer']`、`state['image_urls']`，并落库助手消息
- 图内位置：文旅域共用该节点（旅游侧注册名 `node_answer_output_tourism`），由 `after_rerank` 在 domain=tourism 时指向（main_graph.py:176-192）；结束边直达 END（main_graph.py:197）。文旅确认后若 `state.answer` 已存在，`after_attraction_confirm` 会直接指向该节点（main_graph.py:124-145）。

### 3. Service 总入口
`generate_answer(state)` 是主流程总入口，串联「复用已有答案 → 校验参数 → 构建 Prompt → 生成答案 → 提取图片 → 落库」（answer_output_service.py:21-39）。

### 4. 步骤 1: 复用已有答案
`try_return_existing_answer(state)` 检查 `state["answer"]`：存在时按流式逐字推送（`push_to_session` DELTA + `time.sleep(0.1)`）或非流式 `set_task_result` 直接写任务结果，返回 True 跳过重新生成（answer_output_service.py:42-55）。

### 5. 步骤 2: 校验生成参数
`validate_generation_inputs(state)` 校验 `rewritten_query`（兜底 original_query）非空；`reranked_docs` 为空时生成兜底文档 `{"title":"无","score":0,"type":"milvus","text":"未找到相关资料"}`，并返回 docs/item_names/query/history 四元组（answer_output_service.py:58-70）。

### 6. 步骤 3: 构建答案 Prompt
`build_answer_prompt` 遍历重排文档取前 5 块（reranked_docs[:5]），按「第N块: 标题/得分/来源(网络搜索|向量查询) + 内容」拼为上下文，每块文本截断到 **800 字**（防单块过长拖慢 LLM）；拼接历史文本（`build_history_text`）与主体信息（item_names 为空时提示「未确认具体主体（依据检索内容作答）」），加载 `tourism/answer_out` 模板生成最终 prompt（answer_output_service.py:73-101）。

### 7. 步骤 4: 生成最终答案（SSE 流式 + 引用剥离 + 出处标注）
`final_answer(state, prompt)` 取 `llm_provider.chat().bind(max_tokens=1500)`（限制生成长度）；流式模式下逐 chunk 拼接、以 `SSEEvent.DELTA` 实时推送，**per-delta 用 `_CITATION_PATTERN` 剥离【第N块】/【N】引用标记**（用户流式时也看不到引用角标）；非流式 `invoke(prompt)` 一次返回。完成后 `normalize_answer_text` 压缩空行/清理孤立图片行（answer_output_service.py:104-128）。**随后代码级追加出处标注 `build_source_section(state["reranked_docs"])`**（不依赖 LLM）：遍历精排前 5 块——知识库块（`type != "web"`）收集 `file_title`（携带 `source_path` 时展示为 `文件名（路径：…）`，对齐需求"来源路径或资源链接"；无则只显文件名），列 `- xxx.md（路径：D:/…/xxx.md）（知识库）`，网页块（`type == "web"`）收集「标题 markdown 链接或裸 URL」列 `- [标题](url)（网页）`，两类分别去重；组装为 `\n\n**参考资料**\n- …` 分节，再 `set_task_result` 并写回 `state["answer"]`。无可用出处（均无 file_title/url）时不追加。`final` SSE 事件携带完整 answer，前端以该分节整体重渲染（区分知识库/网页两类来源）。

### 8. 步骤 5: 提取图片 URL
`extract_image_urls(reranked_docs)` 用正则 `\!\[.*?\]\((.*?)\)` 匹配 markdown 图片，并收集以 .png/.jpg/.gif/.jpeg/.svg 结尾的 `url` 字段，去重后写入 `state["image_urls"]`（answer_output_service.py:131-145）。

### 9. 步骤 6: 助手消息落库
`save_assistant_message(state)` 以 role=assistant 保存最终答案、改写问题、item_names 与 image_urls 到历史记录（含 domain 字段）（answer_output_service.py:148-159）。

### 10. 单元测试
该节点文件未内置单元测试。可在统一查询图 `main_graph.py` 中验证：以 tourism 域问题执行 `unified_query_app.stream(...)`，流式更新中应出现 `node_answer_output_tourism` 且 state 含 `answer` 与 `image_urls`；将 `state["answer"]` 预填后直接走 node_rerank → 本节点可验证「复用已有答案」分支（流式逐字推送/非流式直写，answer_output_service.py:42-55）。

### 2.5 P3 确定性分支与限定语（2026-09-04 新增，chitchat_answer_service.py）
`generate_chitchat_answer` 在组装上下文前新增两类**零 LLM 确定性分支**（代码级根治范式：能确定性就不交给 LLM 生成）：

- **指代不明澄清反问（cl-002）**：`is_unresolved_deixis=True` 时返回 `_reply_deixis_clarify(state)` 固定话术"您说的「那边」我还不清楚具体指哪里——请补充一下具体地点（城市或景区名），我再帮您查询。"，落历史后直接 return，不联网、不调模型；
- **未来事件时间问句"无法确认"（neg-004）**：`_FUTURE_EVENT_PATTERN`（发布会/上映/发售/开播/开售/上线等未来事件词）命中时返回 `_TIME_UNCONFIRMED_REPLY`"这类具体活动时间我无法给出确切答案——相关安排可能随官方发布随时变动，请以官方渠道最新消息为准。"，同样零 LLM。教训：首版方案"LLM 作答 + 末尾追加时效限定语"兜不住——模型照样先断言具体日期，judge 仍判 fabricated；只有确定性答复才根治。一般时间问句（"故宫哪年建"类已知史实）不受影响，正常 LLM 作答。

答案生成后追加两类**代码级限定语**（流式同步推 DELTA，非流式写回 answer）：`is_off_domain_product=True` 时追加 `_OFF_DOMAIN_SUFFIX`（域外产品参数"以官方发布为准"，修 neg-002 判定抖动）；命中一般时效问句 `_TIME_SENSITIVE_PATTERN`（什么时候/何时/几号/哪年等，不含未来事件类）时追加 `_TIME_SENSITIVE_SUFFIX`。

### 3. Service 总入口
`generate_chitchat_answer(state)` 是主流程总入口：组装上下文 → 渲染 prompt → 生成回答 → 落库（chitchat_answer_service.py:22-59）。闲聊只消费联网搜索结果，不访问本地知识库（chitchat_answer_service.py:1-3）。

### 4. 步骤 1: 校验问题并取联网结果
校验 `original_query`（兜底 rewritten_query）非空，为空抛 `ValueError`；读取 `state["web_search_docs"]` 并截取前 `CHITCHAT_WEB_TOP=5` 条（chitchat_answer_service.py:31-36）。

### 5. 步骤 2: 拼接联网上下文
`build_web_context(top_docs)` 将每条网页结果拼为「第N条: 标题 + 内容(snippet 或 content) + 来源 URL」的文本；无结果时返回「（无相关联网信息）」占位（chitchat_answer_service.py:62-73）。

### 6. 步骤 3: 渲染闲聊 Prompt
`load_prompt("common/chitchat_answer", question=question, context=context_str)` 加载闲聊回答模板，将用户问题与联网上下文注入 prompt（chitchat_answer_service.py:39-43）。

### 7. 步骤 4: 生成闲聊回答（SSE 流式 + 引用剥离）
`final_answer(state, prompt)` 调用 `llm_provider.chat().bind(max_tokens=1500)`：流式模式逐 chunk 拼接、`is_cancelled` 检测用户停止中断，并以 `SSEEvent.DELTA` 实时推送（per-delta 用 `_CITATION_PATTERN` 剥离引用标记）；非流式 `invoke(prompt)` 一次返回。完成后 `normalize_answer_text` 清理并写回 `state["answer"]`（chitchat_answer_service.py:76-98）。

### 8. 步骤 5: 写回状态并落库
将生成结果写入 `state["answer"]`，`state["image_urls"]` 置空，再以 role=assistant 保存回答到历史记录（rewritten_query=问题，item_names 为空）（chitchat_answer_service.py:48-59）。

### 9. 单元测试
该节点文件未内置单元测试。可在统一查询图 `main_graph.py` 中验证：其 `__main__` 冒烟测试以 `original_query="你好"`（chitchat 关键词）执行，观察执行序列应仅为 `node_intent_route → node_web_search_mcp → node_chitchat_answer`，**不会出现 node_rrf/node_rerank**；最终 state 含 `answer` 且 `image_urls` 为空（main_graph.py:206-222）。

调用 `extract_destination_info(state)`（与天气工具共用一次 LLM 调用 + 进程内缓存），取 `origin`/`destination`；目的地未解析或未提及出发地则跳过并返回空简报（route_tool_service.py:143-151）。

### 5. 步骤 2: 高德地理编码
`amap_geocode(address)` 用高德 `/v3/geocode/geo` 把中文地址转为 (纬度, 经度)（route_tool_service.py:44-68）。出发地编码失败直接放弃（避免报错路线）；**目的地编码未命中时用 LLM 粗略坐标兜底**（校验中国范围内才采纳，route_tool_service.py:157-168）。

### 6. 步骤 3: 驾车路径规划
`fetch_driving_route(origin_geo, dest_geo)` 用高德 `/v3/direction/driving`（extensions=base）取首选路径的 `{distance_km, duration_seconds}`（route_tool_service.py:85-111）。

### 7. 步骤 4: 组装路线简报（含油费估算）
`format_route_text` 拼出「`出发地→目的地:全程约X公里,驾车约X小时X分钟,预计油费约X元（按百公里8L、油价7.8元/L估算）`」；油费由 `distance_km/100 × 油耗 × 油价` 在代码层确定性计算（route_tool_service.py:114-125），`format_duration` 负责秒数转中文时长（route_tool_service.py:71-82）。

### 8. 单元测试
该节点文件未内置单元测试。可在统一查询图以规划类文旅问题（如「从深圳开车去成都，帮我规划一下」）执行 `unified_query_app.stream(...)`，观察 `node_tool_route` 是否产出非空 `tool_route`（日志可见「路线工具:规划成功 深圳→成都」）；未配置 Key 或未提及出发地时应看到对应 warning/info 日志，链路继续不阻断。

## 十三、node_itinerary_generate（规划类：行程拼装答案生成）

> 节点位置：`app/process/unified_query/agent/nodes/node_itinerary_generate.py`
> 所属图：统一查询图 unified_query_app（app/process/unified_query/agent/main_graph.py）
> 调用服务：`app/rag/tourism_query/itinerary_service.py`

### 1. 导入与配置
引入 `sys`、`generate_itinerary`（行程拼装服务）、`node_log`、`add_done_task`/`add_running_task`/`set_task_result`。
- 导入：node_itinerary_generate.py:5-9
- 配置常量（service 侧，itinerary_service.py:24）：`ITINERARY_MAX_TOKENS=2500`（行程内容更长，比普通答案输出的 1500 放宽）
- 引用标记正则 `_CITATION_PATTERN`（流式 delta 级剥离，itinerary_service.py:21）
- 与普通答案输出差异：使用 `tourism/itinerary_out` 专用模板，要求输出结构化行程（概览/每日安排/花销预估/装备注意）（itinerary_service.py:1-6）

### 2. 节点入口函数
`node_itinerary_generate(state)` 是 LangGraph 节点入口：`add_running_task` 标记开始 → 调用 `generate_itinerary(state)` → `add_done_task` 标记完成 → 返回 `{"answer","image_urls"}` 更新。
- 输入：`state['reranked_docs']`、`state['tool_weather']`、`state['tool_route']`、`state['item_names']`、`state['history']`、`state['current_date']`
- 输出：更新 `state['answer']`、`state['image_urls']`，并落库助手消息
- 降级：节点捕获异常写入兜底答复「行程规划生成失败，请稍后重试...」并 `set_task_result`，保证 SSE 会话正常收尾（node_itinerary_generate.py:20-24）
- 图内位置：重排后由 `after_rerank` 在 `domain=tourism` 且 `is_plan` 时指向（main_graph.py:191-193、208）；结束边直达 END（main_graph.py:217）。

### 3. Service 总入口
`generate_itinerary(state)` 是行程拼装主入口，按「构建 Prompt → 模型生成（流式/普通）→ 归一化 → 落库」串联，输出协议与普通答案输出一致（SSE delta + task_result）（itinerary_service.py:64-104）。

### 4. 步骤 1: 构建行程 Prompt
`build_itinerary_prompt(state)` 组装上下文（itinerary_service.py:27-61）：
1. 取 `reranked_docs[:5]`（Top5 重排结果），每块文本截断 800 字，来源标注「网络搜索/向量查询」；
2. 注入工具简报——`tool_weather`/`tool_route` 的 `ok` 时取 `text`，否则占位「（本次无实时天气数据）/（本次无路线规划数据）」；
3. 拼接 `current_date`（时间感知）、`build_history_text` 历史、`item_names` 主体信息，加载 `tourism/itinerary_out` 模板渲染。

### 5. 步骤 2: 模型生成（SSE 流式 + 引用剥离）
`llm_provider.chat().bind(max_tokens=ITINERARY_MAX_TOKENS)`：流式模式逐 chunk 拼接、`is_cancelled` 检测用户停止、`SSEEvent.DELTA` 实时推送并 per-delta 剥离 `_CITATION_PATTERN`；非流式 `invoke` 一次返回（itinerary_service.py:78-89）。完成后 `normalize_answer_text` 清理。

### 6. 步骤 3: 写回状态并落库
`set_task_result(session_id, "answer", ...)` 同步任务结果、写回 `state["answer"]`、`extract_image_urls` 提取配图写入 `state["image_urls"]`，再以 role=assistant 保存到历史记录（含 rewritten_query/item_names/domain）（itinerary_service.py:91-103）。

## 十四、node_datetime_answer（时间/日期确定性直答）

> 节点位置：`app/process/unified_query/agent/nodes/node_datetime_answer.py`
> 所属图：统一查询图 unified_query_app（app/process/unified_query/agent/main_graph.py）
> 调用服务：`app/rag/common/datetime_answer_service.py`

### 1. 定位与背景
**问题**：时间/日期类问句（"今天是几月几号"）曾落入 LLM 兜底，模型凭训练记忆作答（实测答成"8月28日"），且"中秋节是几月几号"曾被误判为文旅触发检索。
**方案**：意图路由第 0.5 层用 `_is_pure_datetime_query()` 前置拦截纯时间询问 → `domain=chitchat` + `is_datetime_query=True`；图内 `route_by_domain` 直接指向本节点——**用系统时钟 `datetime.now()` 确定性计算，零 LLM、零检索、零幻觉**。

### 2. 判定规则（intent_route_service.py）
- 时间询问词（几号/几点/星期几/周几/礼拜几/日期…）+ **时间锚点**（今天/现在/明天/后天/昨天…）命中；
- 排除"活动语境"（几点**出发**/几点**开门**/几点**下班**等，随上文走规划/检索）；
- 无锚点的纯时钟问句（"现在几点"）单独放行；带节日的日期问句（"中秋节是几月几号""国庆节是几号"）由 `_FESTIVAL_NAME_PATTERN` 放行进本节点。

### 3. 确定性解析（datetime_answer_service.py）
- 相对日偏移：大后天/后天/明天/昨天/前天 → `timedelta` 计算目标日；
- 组合输出：日期（X年X月X日）+ 星期（周X）+ 时钟（HH:MM），按问句中出现的询问词拼接；
- 节日映射：公历固定节日（元旦/国庆/劳动节…）直接算本年日期与星期；农历节日（中秋/端午/春节…）只答农历日期并提示"今年公历日期以日历为准"——**不做逐年农历换算，绝不编造公历日期**。

### 4. 输出协议
与闲聊回答一致：流式模式整段推送一次 `SSEEvent.DELTA`（确定性内容无逐字流）；`set_task_result` 写任务结果；role=assistant 落历史（含 domain=chitchat）。结束边直达 END（main_graph.py）。

## 十五、node_clarify（困惑澄清回答）

> 节点位置：`app/process/unified_query/agent/nodes/node_clarify.py`
> 所属图：统一查询图 unified_query_app（app/process/unified_query/agent/main_graph.py）
> 调用服务：`app/rag/common/clarify_answer_service.py`

### 1. 定位与背景
**问题**：用户对上一轮回答表示困惑（实测只输入"？"），此前被 LLM 误判为文旅问题，**把历史行程又完整重生成一遍**，且出现大量连续空行。
**方案**：意图路由第 0.6 层用 `_CONFUSION_PATTERN` 前置拦截（纯"？/？？"符号串、啥意思/没明白/不对吧/再说一遍等极短质疑句）→ `domain=chitchat` + `is_confusion=True`；图内 `route_by_domain` 直接指向本节点——**不联网、不走检索、不重生成行程**。

### 2. 澄清逻辑（clarify_answer_service.py + common/clarify_answer.prompt）
1. 从 Mongo 最近历史中取**上一条助手回答**（无则提示用户说明困惑点）；
2. 注入【当前日期】——若上一条回答含时间/日期表述且与当前日期不符（模型答错日期），要求模型**先明确纠正**；
3. LLM 用大白话重述上一条回答的核心要点（≤150 字），长回答只挑关键、不整篇复读；判断不出困惑点时礼貌请用户换个说法；
4. 流式输出经 `BlankLineCompressor` 压缩连续空行；`normalize_answer_text` 后写回 `state["answer"]` 并落历史。

### 3. 边界
- `_CONFUSION_PATTERN` 全串锚定（`^…$`），"元宇宙是什么意思"等**带主题**的知识型问句不会被误吞，仍走正常检索/闲聊；
- 澄清节点不消费联网结果与本地知识库，纯基于历史 + 当前日期生成。
