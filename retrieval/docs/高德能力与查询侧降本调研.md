# 高德能力与查询侧降本调研

> 主人提问（2026-09-10）：「如果加上高德地图的 skills 能不能减少项目成本？如果可以就也加进计划」
> 调研方式：先定位代码，再下结论。所有行号均基于当前工作树实测。

---

## 零、结论先行

**能降本，但降本来源不是「加高德 MCP」，而是「接上已有门禁 + 扩展现有网关」。**

三句话概括：

1. **项目已经直连高德 REST**（`app/infra/amap_gateway.py`，含限流/退避/降级），再引入第三方 `amap-mcp-server` 等于**多套一层协议 + 多一个 Node 运行时 + 工具 schema 常驻 prompt 吃 token**，对已有能力是**净增成本**。
2. **真正烧钱的是百炼联网搜索 MCP**，且它**目前是文旅链路无条件触发**——这才是成本大头。
3. **最省钱的一档是白捡的**：T5 的 v2 路由已经算出 `source_policy=kb|web|kb_then_web`，**但主图根本没拿它做门禁**（设计成本已付、收益未兑现）。把它接上即可砍掉大量无效 web 调用，工作量约 0.5 天。

## 二、三档降本措施对比

| 档 | 措施 | 省什么 | 工作量 | 风险 | 性价比 |
|---|---|---|---|---|---|
| **D0** | 接上 `source_policy` 门禁：`kb` 不联网、`kb_then_web` 仅 KB 空/低分才联网、`web` 才直接联网 | 砍掉文旅全量无效 web 调用（0.029 元/次） | **0.5 天** | 极低（逻辑已存在，只差接线） | **最高，白捡** |
| **D1** | 扩展现有 `amap_gateway`：接入 `search_poi` / `poi_detail` / 公交规划 / 批量测距，让「景点地址·门票·开放时间·周边美食酒店·景点间距离」走结构化接口 | 再砍一批 web 调用 + **省网页长文本进 context 的 token** + 提升准确率（结构化 > 网页摘要） | 1.5 天 | 低（照 amap/weather 网关范式，失败 `ok=False` 不阻断） | 高 |
| **D2** | 引入第三方 `amap-mcp-server`（Node.js ≥18 子进程） | — | 1 天 | 中 | **不推荐** |

### 为什么 D2 不推荐（诚实说明）

| 维度 | 直连 REST（现状） | 第三方 MCP 封装 |
|---|---|---|
| 协议层 | 一次 HTTP GET | MCP 握手 + 工具发现 + 子进程常驻 |
| 运行时 | 纯 Python，无新增依赖 | 需 Node.js ≥18 |
| Token 开销 | 0 | 工具 schema 与结果常驻 prompt，**每轮多几百 token** |
| 费用 | 高德免费额度内 | 部分商业化封装 **0.002 元/次**（把免费额度变成按次付费，**是升本**） |
| 可控性 | 网关已有限流/退避/降级 | 子进程崩溃需额外守护 |

> 另有商业化封装宣称「0.002 元/次、含 10 万次/月免费、比原生便宜 47%」——**这是第三方转售，不是高德官方**，且本项目本就在免费额度内，接入即是从 0 元变成付费。**切勿采信此类宣传口径。**

## 三、量化测算（估算，需埋点校准）

**假设**（待埋点校准，见第五节）：日查询 1000 次，文旅占 90%（900 次），闲聊 10%。

| 场景 | web search 次数/天 | 月费用（29 元/千次） |
|---|---|---|
| **现状**（文旅全量 + 闲聊全量） | ≈ 900 + 100 ≈ **1000** | ≈ **870 元/月** |
| **D0 后**（kb 类不联网，估砍 50%） | ≈ 500 | ≈ **435 元/月** |
| **D0+D1 后**（POI 类再走高德，估再砍 30%） | ≈ 350 | ≈ **304 元/月** |

**年化节省约 4000~5000 元**（按上述假设）。

> ⚠️ 诚实标注：
> 1. 这是**量级估算**，真实比例取决于 query 分布，必须埋点后才能定论。
> 2. 2000 次免费额度内不产生费用——**当前开发/评测阶段基本不花钱，成本只在真实用户量上来后显现**。故此项属「上线前必须做，但不是现在最紧急」。
> 3. **Token 成本不是大头**：qwen-plus 输入 0.8 元/百万 token 级别，网页摘要进 context 的 token 费用远低于 0.029 元/次的调用费。D1 的 token 节省是顺带收益，主收益仍是调用费与准确率。

### 7.2 两个**实测校准**（按文档直觉写会踩坑）

1. **测距端点参数方向与直觉相反**：`v3/distance` 是 **多 `origins` + 单 `destination`**。
   实测 `origins` 单个 + `destination` 多个（"|" 分隔）→ `INVALID_PARAMS(20000)`；
   调换后正常返回，`distance` 单位**米**、`duration` 单位**秒**，结果带 `origin_id`（1-based）可按序对回起点。
2. **POI 关键词必须换**：单用 `"景点"` 召回的是「成都金融城双子塔（商务写字楼）」「交子公园」等**非景区**；
   换成 `旅游景区|热门景点|名胜古迹` 三词合并去重后，得到 都江堰景区 / 熊猫基地 / 宽窄巷子 / 武侯祠 / 文殊院 / 杜甫草堂等真实景区。
   另加"行政区以『区』结尾＝市区优先"排序，保证市区行程先拿到核心景点而非远郊。
3. **`biz_ext` 字段名勿臆测**：开放时间在 `open_time`（另有长文案 `opentime2`），`cost` 无数据时高德返回**空列表 `[]`**（须丢弃）。

## 六、硬约束（不可违反）

- D0 门禁**不得**削弱「域外/时效类问题必须联网」的能力（neg-002 判例：联网作答属设计行为）。门禁只砍 `source_policy=kb` 的无效调用。
- D1 高德返回失败时，**必须 `ok=False` 降级不阻断**，绝不冒充数据（延续 amap/weather 网关既有约定）。
- POI 类数据须标注来源（如「来源：高德 POI」），票价/营业时间等易变信息须带「以实际为准」限定语，**严禁无数据时让模型估算票价**（与 T14 同一条不编造红线）。
