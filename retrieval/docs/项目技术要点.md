## 一、检索问答链路（RAG 核心）

### 1. 统一意图路由：分层漏斗，规则优先、LLM 兜底

**是什么**：一个问题进来，先过层级判定决定走文旅还是闲聊链路——
第零层规划句式正则（`is_plan`）→ 追问继承（域记忆）→ **第 2.5 层指代不明确定性澄清** → 关键词规则 → LLM json_mode 兜底（带缓存 + 知识型句式推翻）。

**为什么值得学**：
- 大多数问题在规则层就出结果，LLM 只为长尾问题付费——平均延迟与 token 成本可控；
- 澄清反问、域外拦截是**零 LLM** 的确定性输出，可测、稳定、不抖动；

**代码**：
- 总入口 `classify_intent`：`app/rag/common/intent_route_service.py` L342-420（模块末尾）
- 指代不明澄清正则 `_DEIXIS_CONSULT_PATTERN`：L125（"那边/那里/当地"开头直接反问，不检索）
- LLM 兜底：`classify_by_llm` L283-298、`_call_intent_model` L259-280（json_mode + `cached_invoke` 缓存）
- 图侧薄封装：`process/unified_query/agent/nodes/node_intent_route.py`（服务与图解耦的范例）

### 2. 四路并行召回 + RRF 同步屏障 + 跨源统一精排

**是什么**：文旅提问**恒定四路并行**（向量 + 多改写 HyDE + BM25 + 联网）；本地三路在 RRF 汇合成一个排名，再与联网结果一起进 Rerank 统一打分。

**为什么值得学**：
- LangGraph 的超步（super-step）天然表达"多路同时跑、到 RRF 集合再继续"——并行不写线程池代码，条件边表达"哪些路要跑"（闲聊不检索本地库、is_plan 追加两个工具路）；
- **联网不进 RRF 是刻意设计**：RRF 要求同一 ID 空间内排名可比，网页没有 `chunk_id`、分数体系不同，硬融会稀释本地排名；联网改为在 Rerank 阶段与本地候选进同一打分体系——"可比性"决定融合层级。

**代码**：
- 图编排：`process/unified_query/agent/main_graph.py`——`after_attraction_confirm` L148-159（四路恒定，is_plan 在 L157-158 追加天气/路线两工具路）、静态汇聚边 L195-204（RRF 为同步屏障）、`after_rerank` L208-215（按域+is_plan 分发答案生成）
- RRF：`rag/common/rrf_service.py` `fuse_by_rrf`（倒数排名融合 1/(k+rank)，纯本地计算）
- 精排分发：`rag/common/rerank_service.py` `rerank_documents` L54

### 3. HyDE 多改写 + 批量编码

**是什么**：一次 LLM 调用把问题改写成 3 条查询 + 1 段"假设答案"（HyDE，用答案句式去够答案所在区域）；3 条改写**合并成 1 次编码调用**。

**为什么值得学**：BGE-M3 推理有全局锁，逐条编码是串行的；批量编码把 3 次模型调用压成 1 次——这是"了解模型服务特性后再做工程优化"的典型样本。另注意短查询/已有主体时跳过多改写（省一次 LLM，见 `main_graph.py` 条件跳过 L121-130 一带）。

**代码**：`rag/common/multi_query_service.py` L160-162（批量注释说明）、L174（批量调用）；文旅域一份 `search_embedding_hyde_service.py`（连 `tourism_chunks` 集合）。

### 4. BM25 进程内倒排索引

**是什么**：用 jieba + rank_bm25 在**进程内**为整个知识库建倒排索引（TTL 600s），专有名词精确命中不依赖向量。

**为什么值得学**：向量检索"意近词不同"强、**专有名词弱**（学习型稀疏也补不全）；BM25 是成本几乎为零的字面兜底路。进程内索引 + TTL + 主动失效接口（配合要点 11 的版本广播）是缓存管理的完整闭环。

**代码**：`rag/common/bm25_service.py` `get_bm25_index` L208-246（建索引+TTL 判定）、TTL 常量 L33、`invalidate_bm25_cache` L249-261。

### 5. Rerank 零 LLM 抽取式压缩（性能治理案例）

**是什么**：超长候选进 Reranker 前，用**句子级抽取式压缩**（按与问题的相关性抽句拼回）替代历史上的"串行 LLM 精简"。

**为什么值得学**：这是全项目最有代表性的**性能治理故事**——旧方案每个超长候选调一次 LLM，实测最多 9 次、累计 30-48 秒，是全链路最大瓶颈；抽取式压缩零模型调用、毫秒级完成，且先按字符数粗筛让多数候选根本不进压缩。方法论：**瓶颈治理先量化、再找"不调模型"的替代、最后加粗筛短路**。

**代码**：`rag/common/rerank_service.py`——docstring L5-12 记录了这段历史；`condense_text_for_rerank` L211-266；粗筛 `collect_oversized_items` L285 与 L343 调用处。

### 6. 规划类问题：天气/路线/行程三件套并行编排

**是什么**：识别出 `is_plan` 后，检索层额外并行追加"和风天气 + 高德路线（含代码级油费估算）"两个外部工具，结果与四路检索一起汇入 RRF，最终由结构化行程模板拼装答案。

**为什么值得学**：
- 外部 API 与检索**并行**而非串行——工具不拖慢主链路；
- **防编造三件套**：① 无 KB 素材直接拒答（`_check_kb_material_gate`，注意教训：正文子串出现 1 次就放行会被"中国的马尔代夫"式修辞骗过，判据必须更严）；② LLM 生成的班次号约束不住时**代码级剥离**（`_strip_flight_train_numbers`，prompt 遵循度不足永远存在，关键结论要走代码）；③ 单程/往返 A/B 形态分支（"我在X/到了X"禁返程段）。

**代码**：`rag/tourism_query/itinerary_service.py`——素材闸门 L120、班次剥离 L85、闸门调用 L215、出口统一消毒 L259；`weather_tool_service.py`（天气/路线共用一次 LLM 行程解析 + 缓存）；`route_tool_service.py`（高德 + 油费估算）。

### 7. 负向护栏体系：拒答/澄清/防编造用确定性答复根治

**是什么**：四类负向场景各有确定性出口——未来事件（"发布会/上映"）直接"无法确认"；域外产品词命中标记后闲聊兜底并加"以官方发布为准"限定；代办/预订类先声明能力边界再答；指代不明确定性反问。

**为什么值得学**：**最重要的教训是 neg-004**——先用"限定语提示"（答里加"据现有资料"）想压住编造，评测发现模型会"先断言后提示"，LLM judge 照样判编造；换成**确定性答复**（命中正则直接返回模板话术，不进生成）才根治。结论：**对"绝不能发生"的行为，用代码拦截，不用 prompt 祈祷。**

**代码**：`rag/common/chitchat_answer_service.py`——未来事件正则 L42 + 拦截 L75、域外产品标记 L105；`rag/tourism_query/answer_output_service.py`——能力边界声明 L25 + 注入 L146；澄清节点 `process/unified_query/agent/nodes/node_clarify.py`（零 LLM）。

### 8. SSE 流式输出 + 停止生成

**是什么**：/query 同步与 /stream SSE 双模式共用同一条查询链路；SSE 五类事件（ready/progress/delta/final/error），用户可随时 /stop 中断。

**为什么值得学**：流式不只是"打字机效果"——`ready/progress` 事件把图节点的执行进度实时推给前端（配合 done_list），用户体感的"系统在干活"来自这里；停止标记用独立存储（`clear_cancel`），每个节点推进时检查。

**代码**：`app/api/http/query_server.py`——`invoke_query` L89（两模式公共入口）、`/query` L331、`/stream/{sid}` L348、`/stop/{sid}` L365；`app/shared/utils/sse_utils.py`（事件封装与推送）。

## 二、导入链路

### 9. 多格式解析管线 + 多模态前置转写

**是什么**：七类上传格式四条解析管线——PDF（MinerU 云端 API）、文本族 txt/json/html/docx（纯规则代码）、表格 xlsx/csv（pandas）、**图片（Qwen3-VL 视觉转文字）在导入服务层前置转写为 Markdown**，之后全部走同一条 md → 切分 → 向量 → 入库链路。

**为什么值得学**：
- **多模态前置**让导入图零改动支持图片——格式差异消灭在服务层，图只认 md；
- docx 内嵌图要下到 XML 层抽（python-docx 的 `qn()` 不注册 VML 的 `v` 前缀，需用 Clark 全名 `{urn:schemas-microsoft-com:vml}imagedata`）。

**代码**：`rag/common/image_ocr_service.py`（VL，单图 7MB 上限）；`rag/common/text_parse_service.py`（docx/html 抽图，`_extract_docx_images_in_paragraph` 等）；`rag/common/pdf_parse_service.py`（MinerU 上传+轮询+解压）。

### 10. 双集合分层 + BGE-M3 双向量 + 幂等入库

**是什么**：文旅域两个 Milvus 集合——`tourism_chunks`（正文切块，承载召回）与 `tourism_entity`（主体索引，景点级）；BGE-M3 同时产出 dense+sparse 双向量做 hybrid_search。

**为什么值得学**：
- 分层让"先毫秒级定位主体、再限定范围检索"成为可能（主体确认打小集合，不打全库）；
- 主体与正文**一致性保障**：主体入库失败**硬终止整个任务**，防"chunks 有、entity 无"的半成品知识（半成品 = 检索永远对不齐的隐性 bug 源）；
- 覆盖式幂等入库（同名重导不重复堆积）。

**代码**：`rag/tourism_import/index_service.py`、`embedding_service.py`；元数据抽取 `tourism_meta_extract_service.py`（Pydantic schema + LLM json_mode）。

## 三、工程化与可靠性

### 11. 缓存体系全景：进程内缓存 + 跨进程版本广播

**是什么**：两层缓存策略——
① 进程内：启动预热（五项：BGE-M3/jieba/Milvus/BM25/LLM 客户端）+ LLM 结果缓存（TTL 600s+LRU，接入意图/改写/行程解析三点）+ BM25 索引 TTL；
② **跨进程**：导入服务与查询服务是两个独立进程，导入完成后用 **Mongo 版本号广播**（`app_meta` 集合）通知查询进程刷新三件套缓存——导入成功 → 本进程清理 + bump 版本；查询入口 5s 节流比对，版本变了才刷新。

**为什么值得学**：
- 版本号广播是**无新中间件的最终一致**：复用已在用的 Mongo、天然支持查询服务多实例（各自基线独立比对）、Mongo 挂了静默降级为 TTL 兜底不阻断主链路；
- 设计节奏值得抄：**读便宜的（版本号）高频、刷贵的（三件套）低频**；失效函数幂等所以无锁并发安全；
- 更深的教训：三个缓存失效函数曾"定义了但全项目零调用"——**写了缓存就要写失效路径，否则缓存是负资产**。

**代码**：`app/shared/runtime/data_version_service.py`（bump L62-81 / get L84-100 / notify L126-141 / 节流检查 L144-176）；挂钩 `app/api/http/import_server.py` L222-224（run_graph_task 成功路径）与 `app/api/http/query_server.py` L103（invoke_query 开头）；预热 `app/shared/runtime/warmup.py` `warmup_all` L90-125；LLM 缓存 `app/shared/runtime/llm_cache.py` `cached_invoke` L104-131。

### 12. 降级纪律：任何辅路失败都不拖垮主链路

**是什么**：全项目统一遵守"失败降级、不抛异常、不阻断"——联网 2.5s 超时熔断降级空列表；天气/路线工具失败降级为"无参考"；历史记录读写失败返回默认值；LLM 全部调用带缓存与降级。

**为什么值得学**：RAG 系统是"本地主链路 + N 条辅路"的形态，辅路的可用性永远低于主链路；**每条辅路都要回答"挂了怎么办"**，且答案必须是代码级的（超时熔断、空值降级），而不是"应该不会挂"。另配套：导入并发信号量（防打爆 LLM 速率）+ 429 指数退避。

**代码**：`rag/common/web_search_service.py` L26（熔断阈值）、L102-104（超时降级）；`api/http/import_server.py`（`_IMPORT_CONCURRENCY_SEMAPHORE` + run_graph_task）；`rag/tourism_query/weather_tool_service.py` / `route_tool_service.py`（try/except 降级模式模板）。

## 四、质量保障

### 13. 评测驱动迭代：40 题金标集 + 轻量基准 + judge 方法论

**是什么**：
- **正式评测**：`data/eval_cases.json` 40 题（正 32 + 负 6 + 澄清 2），**金标逐条对齐库内 chunk 原文**（golden_file_titles + golden_facts 取自真实入库内容，不手写空想），`run_eval.py` 全链路串行执行（检索 B3 F1/Hit + 问答分域 Acc/P/R/F1）；
- **四轮走势**：Acc 0.8750 → 0.8000（发现缓存失效 bug 后一度下滑）→ 0.9500 → **1.0000**（每轮问题清单逐条闭环）；检索 F1@5 0.8135 / Hit@5 1.0；
- **轻量基准**：`data/eval/bench/run_bench.py` 12 条、标准库直打 /query，报 mean/P50/P95 延迟 + fact_hit_rate + 真实率，用于日常快速回归（与全量评测互补）。

**为什么值得学**：
- **金标来源纪律**：评测题取材自"库内真实 chunk 原文"（有专门 dump 脚本取证），不凭空编题——否则评的是想象中的系统；
- **LLM judge 只当初筛**：曾实测 judge 失守率 17.5%（FP/TN 双向漏判），终值必须人工抽检 ≥25%；
- **负例与澄清用例的价值 ≥ 正例**：六个负例倒逼出整个护栏体系（要点 7），"拒答的准确性"是 RAG 系统可信度的一半。

**代码**：`data/eval_cases.json`（40 题全量）；`data/eval/run_eval.py`（串行执行 + 分域指标 + 定向回归 `--ids`）；`data/eval/bench/run_bench.py`（延迟分位 + judge 双指标）；历史成绩 `output/eval/20260904_full_v4_final/`。

## 五、给新人的学习路径建议（一天路线）

1. **先跑通再读码**（1h）：PyCharm 起双服务 → chat.html 提三个问题（文旅攻略 / "明天北京天气怎么样帮我规划"）→ 打开 `/stream` 看事件流。
2. **横读主图**（2h）：`process/unified_query/agent/main_graph.py` 从 `route_by_domain` L90 到 `after_rerank` L208 通读——所有分支逻辑都在条件边函数里，读图即读业务。
3. **纵读两链**（3h）：意图路由 `intent_route_service.py` `classify_intent` L342 → 检索四路 → `rerank_service.py` → `answer_output_service.py`；再走导入线 `import_server.py` → 一条解析管线 → `index_service.py`。
4. **跑一次评测**（1h）：`python data/eval/run_eval.py --cases data/eval_cases.json --out output/eval/<你的时间戳>`，对照 40 题理解每类用例在考什么。
5. **读两篇"教训型"代码**（1h）：`rerank_service.py` docstring（性能治理）与 `chitchat_answer_service.py`（确定性护栏）——这两个文件里沉淀了本项目最贵的经验。

> **约定提醒**：① 新增缓存必须同时写失效路径；② 辅路失败必须降级不阻断；③ 涉及"绝不能发生"的行为用代码拦截不用 prompt；④ 改动行号后同步各文档引用（本项目文档全部带行号索引）。
