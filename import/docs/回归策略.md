# 分层回归策略（L0 / L1 / L2 / L3）

> **为什么要有本策略**：全量 50 题评测约 11.6 分钟（实测 698.2s / 50 条 ≈ 14s/条）+ 50 次 LLM judge 调用。
> 日常每个任务都全量跑，既费时又耗 token 额度——额度紧张时 judge 无响应会造成**假 FN 抖动**，反而误导判断。
> 主人 2026-09-10 明确：**不要每次全量跑，只为新功能做单测或连续多任务后全量**。
> 本策略把回归拆成四层，配套自动化工具，全量改为「里程碑才跑」。

---

## 一、四层定义

| 层 | 名称 | 触发时机 | 工具 / 命令 | 耗时 |
|---|---|---|---|---|
| **L0** | 秒级静态单测 | 每次改完代码立即跑（CI 级） | `python test/test_graph_state_keys.py` | <1s |
| **L1** | 定向选集（按影响面） | 改了某模块，只跑受影响的用例 | `python data/eval/pick_cases.py --impact <影响面>` | 按选集 |
| **L2** | core-20 核心基线 | 连续完成多任务、合饭前 | `python data/eval/pick_cases.py --impact core` → 喂 `run_eval --ids` | ≈4.7min |
| **L3** | 全量 50 题 | 里程碑 / 发版 / 架构变更后 | `python data/eval/run_eval.py` | ≈11.6min |

**默认工作流**：改代码 → **L0 必过** → 按改动面跑 **L1** → 连续多任务后跑 **L2** → 里程碑跑 **L3**。

---

## 二、L0：state 键声明一致性扫描（秒级，零 LLM / 零 Milvus）

- 文件：`test/test_graph_state_keys.py`（纯 AST 解析，**不 import 任何业务模块**，故不加载模型、不连 Milvus）。
- 作用：LangGraph 对未声明的 state 键会**静默丢弃写入**（曾两次踩坑）。本测试把这类风险从「靠人工读评测结果」变成秒级自动拦截。
- 扫描范围：两个图 state 定义 + `app/process/unified_query/agent/nodes` + `app/rag/tourism_query` + 若干公共服务层文件（`QUERY_SCAN_DIRS` / `QUERY_SCAN_FILES`）。
- 关键键兜底断言（`CRITICAL_KEYS`）：即使特殊写法（如 `result[...]` 中间变量回填）导致静态漏检，这些键一旦从 TypedDict 消失也立即失败：`answer / domain / rewritten_query / history / is_plan / route_info / reranked_docs / rrf_chunks / web_search_docs / tool_weather / tool_route`。
- 已知缺失（`KNOWN_MISSING`，不阻断）：`item_names`（`attraction_confirm_service.py:164` 写入、`:182` 同函数内读取，下游不读，暂无功能影响；但未来下游若按它定向检索会静默失效，是否补声明待主人定）。
- 验证结果（2026-09-10）：声明的 state 键 25 个、扫描 node 文件 15 个、node 写入键全部已声明、14 个关键键齐全 → **全部通过 ✅**。

---

## 三、L1 / L2：按影响面选集（`pick_cases.py`）

- 配套数据：`data/eval_cases.json` 的 `meta.tag_schema` + `meta.core_set`（core-20）。
- `IMPACT_MAP`（改动影响面 → 标签并集）：

| impact | 含义 | 必跑场景 |
|---|---|---|
| `routing` | 路由判定敏感 | 改 `intent_route_service` / 路由正则 / `intent_route_v2.prompt` |
| `retrieval` | 检索与重排敏感 | 改 embedding / bm25 / rerank / 集合 |
| `generation` | 答案生成敏感 | 改 answer prompt / `answer_output_service` |
| `plan` | 行程规划敏感 | 改 `itinerary` / `trip_plan` |
| `web` | 依赖联网结果 | 改 web 链路 / T15 `source_policy` 门禁 |
| `guard` | 拒答与闲聊护栏 | 改负类 / 澄清判定 |
| `core` | 强制并入 core-20 | 任何合饭前基线 |

- 用法：
  ```bash
  # 改了路由 → 只跑路由敏感用例
  python data/eval/pick_cases.py --impact routing
  # 改了答案 prompt（影响面最大，并上 core）
  python data/eval/pick_cases.py --impact generation --core
  # 自定义标签并集
  python data/eval/pick_cases.py --tag cross,web
  # 只看清单与预估耗时，不取 id
  python data/eval/pick_cases.py --impact core --list
  # 直接喂给 run_eval（bash）
  IDS=$(python data/eval/pick_cases.py --impact routing)
  python data/eval/run_eval.py --cases data/eval_cases.json --out output/eval/xxx --ids "$IDS"
  ```
- 选集输出逗号分隔 id 串（stdout），辅助信息走 stderr，便于 shell 直传。
- 验证（2026-09-10）：`--impact core --list` 命中 20 条、预估 4.7 分钟，清单与 `meta.core_set` 一致 ✅。

## 四、L3：全量提速（`run_eval.py --workers`）

- 新增 `--workers`（默认 1 串行）。`>1` 时走 `ThreadPoolExecutor` 并发（IO 密集的 LLM/联网调用适合线程池），安全上限 3，且**错峰启动**（每条 `sleep(idx*0.25s)`）降低瞬间打满 LLM 供应商触发 429 的概率。
- ⚠️ **风险自负**：并发会提高 429 概率，judge 无响应 → 假 FN。仅在额度充足、需提速时用 2~3；日常 L2 已足够。
- 串行路径（`workers=1`）行为完全不变，零扰动。

---

## 五、铁律（踩坑所得，复用于所有层）

1. **LangGraph state 键必须 TypedDict 显式声明**，否则写入静默丢弃。
2. **评测不达标先定向复跑区分「抖动」与「真回归」**：`neg-002` 曾属 judge 抖动或金标不当，非代码回归。judge 只当初筛，终值须 L3 人工抽检 ≥25%。
3. **收口 = 打勾 + 提交 + 写工作日志**，缺一不算完成。
4. **硬约束**：任何 B 系（T5/T6/T7）合并前，40 题评测必须保持 Acc 1.0 基线；新功能不得让老用例退化。

---

## 六、与任务清单 / T8 的关系

- 本策略对应任务清单 **T16（分层回归脚手架）**，随 L0/L1/L2/L3 工具落地完成。
- T8 已确认「导入端与查询端代码层零交叉引用」，`pick_cases.py` 与 `run_eval.py` 不区分部署角色，对所有用例一视同仁；若后续做 Import / Retrieval 物理目录拆分（见洽主人决策），本策略工具无需改动，仅 `QUERY_SCAN_DIRS` 需随之调整扫描路径。

## 七、L3 人工抽检与 A/B 对比（工具化，2026-09-10 夜新增）

> 第四章第 2 条要求「终值须 L3 人工抽检 ≥25%」，此前**无工具支撑**（手工挑样本 + 手工记账）。现已工具化：

### 7.1 L3 抽检：`data/eval/make_review_sheet.py`

```bash
# 1) 生成复核单（必含全部 FAIL 项 + 随机补足至 ≥ratio；同 seed 可复现）
python data/eval/make_review_sheet.py --out output/eval/<ts> --ratio 0.25 --seed 42
#    → output/eval/<ts>/review_sheet.md   （逐条留证：问题 / 模型答案 / 金标要点+covered / judge 理由 / 人工判定栏）
#    → output/eval/<ts>/review_sample.json（抽样留痕：seed / 比例 / judge 基线指标 / picked id）

# 2) 回填人工结论（correct=模型答对 / wrong=模型答错；未填的沿用 judge 原判）
#    先写 output/eval/<ts>/review_result.json： {"plan-001": "wrong", "neg-003": "correct"}
python data/eval/make_review_sheet.py --apply output/eval/<ts> \
    --verdicts output/eval/<ts>/review_result.json
#    → output/eval/<ts>/corrected_metrics.json（judge 原判 vs 修正后 四格/Acc/P/R/F1，含 human_flipped）
```

口径与 `run_eval.aggregate_answer_metrics` **严格一致**（正类 = `expect_type ∈ {answer, plan}`）。

### 7.2 A/B 对比：`data/eval/compare_eval.py`

```bash
python data/eval/compare_eval.py --base output/eval/A --new output/eval/B [--show-flips] [--json diff.json]
```

输出指标 Δ 表 + 逐用例翻转（改善/回归）；用例集合不一致时**仅对共同用例**计算并单列独有 id；出现「回归」返回码 1（可接 CI）。
典型用途：**开关对照**（如 `INTENT_ROUTE_LLM_FIRST` ON vs OFF）、改动前后回归定位。

### 7.3 质量门禁：`scripts/run_quality_gate.py`

```bash
python scripts/run_quality_gate.py --fast     # 仅纯离线单测（推荐：评测进行中也安全）
python scripts/run_quality_gate.py            # 全量：全部 test_*.py
```

### 7.4 ⚠️ 并发纪律（本次实测踩坑，务必遵守）

| 规则 | 原因 |
|---|---|
| **同一时间只跑一个 `run_eval.py`** | 两个评测进程会争抢同一 LLM 配额 → 429 → 出现假 FN / judge 失败（`unresolved`） |
| **评测期间不要跑需真实 LLM 的单测**（如 `test_tool_weather.py`） | 同样争抢配额 → 测试假阳性失败（非代码回归）。改用 `--fast` |
| **评测输出目录不要复用** | 同名目录会被后完成者覆盖，出现「stdout 指标 ≠ metrics.json」的假象 |

> 自检方法：对 `metrics.json` 的 `cases` 复算四格，与 `summary.answer_global` 对照是否自洽（本次据此判定**已落盘结果可信**、stdout 差异来自并发污染）。

### 7.5 评测口径提示

- `unresolved`（judge 调用失败 / L1_only 未判）**不计入分母**。故 judge 侧大面积失败时，Acc 会「看起来更好」——复跑前先看 `unresolved` 计数。
- plan 类现有 **L1 结构前置门禁**（`_PLAN_STRUCTURE_ENFORCE`）：「该出行程却走普通问答」直接判 `accept=False`（`method=L1_plan_structure`）。
