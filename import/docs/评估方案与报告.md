## 1. 评估目标与总体思路

本系统是文旅单域 RAG 应用（LangGraph 统一查询图 + 文旅 Milvus 集合）。评估要回答两个问题：

1. **能不能交付**：以可复现、口径显式的硬指标（准确率 / 精确率 / 召回率 / F1）证明当前质量达到可用门槛。
2. **好在哪**：通过"同数据同问题的消融对照 + 架构级横向对比"，说明相对"通用 LLM"和"通用 RAG 框架/纯向量检索"的结构性优势。

### 1.1 评估设计原则

| 原则 | 落地方式 |
|---|---|
| 分层评估，不做端到端一锅烩 | 检索层与问答层各自定义指标（检索差与生成差归因分离） |
| 指标口径显式化 | 每个 TP/FP/FN/TN、P/R/F1 的分子分母写死，见第 3 节 |
| 对抗性用例 | 评测集必须含负例/边界：需澄清、需拒答、闲聊、越权、规划——只测正例会高估质量 |
| 可复现 | 固定评测集 JSON + 固定参数（LLM judge temperature=0）+ 运行信息卡（日期/commit/环境）落盘 |
| 真实语料 | 金标来源文件均取自已导入 Milvus 的真实资料（见第 2 节），不凭空编造 |

### 2.2 单条用例 schema

```json
{
  "id": "tr-001",
  "domain": "tourism",            // tourism | chitchat | plan
  "intent": "fact",               // fact | confirm | compare | plan | chitchat | datetime | clarify | refuse
  "query": "成都有哪些必去的景点？",
  "golden_file_titles": ["成都景点推荐"],            // 检索层相关来源（Milvus file_title，不含扩展名）
  "golden_facts": ["宽窄巷子、武侯祠、锦里等为成都代表性景点"],  // 问答层要点，LLM-judge 逐条核对
  "expect_type": "answer",         // answer | clarify | refuse | chitchat | plan
  "difficulty": "easy | mid | hard",
  "notes": "主体确认后直答；验证 content_type 元数据透传是否生效"
}
```

### 2.3 取材来源（已入库真实资料，file_title 示例）

- 文旅：`成都景点推荐`、`成都美食推荐`、`云南交通指南`、`杭州线路推荐`、`厦门住宿推荐`、`张家界交通指南`、`张家界住宿推荐`、`中国西部十大著名旅游景点`、`川西小环线5天深度旅游攻略`、`日本京都深度旅游攻略` 等。
- 文化类 PDF：`70个中国文化常识`、`中国传统丧葬全过程与民间风俗礼仪` 等（按 content_type 归入文化知识介绍）。

> 金标撰写规则：每条问题的 `golden_facts` 必须能从 `golden_file_titles` 对应 chunk 正文中找到依据；检索层只认来源文件级相关（不精标到 chunk，标注成本与可判性平衡）。

### 2.4 正负样本判定口径（重要）

- **正例**：库内确有答案，期望输出"基于库的实质回答"。
- 负例：期望不给库内容（拒答/澄清/闲聊），例如问与知识库无关内容、诱导越权（如把殡葬风俗资料当文旅推荐输出）、多景点歧义未确认主体。
- 正负例同时进入同一套 P/R/F1，防止"系统只会答或只会拒"的偏科模型拿高分。

## 3. 硬性指标定义（准确率 / 精确率 / 召回率 / F1）

### 3.1 检索层指标（top-k = 5，即最终送入答案生成的 reranked_docs[:5]）

单条 case：
- 候选集 A = 精排后前 5 块的来源 `file_title` 去重集合；
- 相关集 G = `golden_file_titles`；
- 命中 I = A ∩ G。

| 指标 | 公式 | 含义 |
|---|---|---|
| Precision@5 | |I| / |A| | 召回的 5 块里多少是相关来源（去噪能力） |
| Recall@5 | |I| / |G| | 相关来源被召全多少（漏检能力） |
| F1@5 | 2PR/(P+R) | 综合 |
| Hit@5（本方案"检索准确率"） | 该 case 是否 |I| ≥ 1（0/1） | 至少一条相关进答案上下文，取宏平均 |

汇总口径：**macro（按 case 平均）为主指标，micro（合并混淆）为辅**。

### 3.2 问答层指标（生成结果正确性，case 级二分类）

把每个 case 按"期望是否给实质内容"分成正类/负类，得到四格：

| | 预测：给了实质回答 | 预测：拒答/澄清/闲聊 |
|---|---|---|
| **实际：正例**（该答） | TP | FN（漏答/答非所问/幻觉也计 FN） |
| **实际：负例**（不该答） | FP（误答/编造/越权） | TN |

| 指标 | 公式 | 在本系统的工程含义 |
|---|---|---|
| 准确率 Accuracy | (TP+TN)/N | 全部用例里行为正确的比例 |
| 精确率 Precision | TP/(TP+FP) | "开口就说对/不胡说"——防幻觉、防越权 |
| 召回率 Recall | TP/(TP+FN) | "该答的都答上"——不漏答、不错误拒答 |
| F1 | 2PR/(P+R) | 综合平衡 |

### 3.3 单条答案"对错"判定方法（三级流水线）

1. **L1 结构/规则硬校验（不花 token，先判）**
   - 该拒未拒、该澄清未澄清 → 直接判负；
   - 正例答案缺失出处（`参考资料`/`—— 内容来自`）→ 记缺陷，若 golden_facts 也不命中则判负；
   - 出处列出的 file_title 与 G 完全不相交 → 判负（用了不相关来源 = 答非所问）。
2. **L2 LLM-as-Judge（复用项目 llm_provider，temperature=0，专用 judge prompt）**
   - 把 `golden_facts`、`golden_file_titles` 对应原文、模型答案一并交给 judge；
   - 判定：a) 要点是否覆盖（逐条 0/1）；b) 是否有**超出给定原文**的断言（幻觉检测）；c) 综合 accept 0/1。
   - judge 只做"核对员"，不做开放式打分，降低偏置。
3. **L3 人工抽检**：对 L1/L2 一致判负与随机 ≥20% 的 case 人工复核，结果记入报告"人工复核记录"节，分歧以人工为准并修正脚本口径。

> 不用 BLEU/ROUGE 做主指标的原因：生成式回答措辞多样，逐字 n-gram 相似度会系统性低估"答对但换说法"的正确回答；仅作附录参考，不计权。

### 3.4 可交付验收线（建议值，待评审确认后写死）

| 层级 | 指标 | 建议门槛 | 说明 |
|---|---|---|---|
| 检索（全域） | Hit@5 / F1@5 | ≥ 0.90 / ≥ 0.80 | Rerank 断崖截断保证 Top5 高相关 |
| 问答（全域） | Accuracy / F1 | ≥ 0.85 / ≥ 0.85 | |
| 问答（文旅分域） | F1 | ≥ 0.85 | |
| 负例 | FP 率（误答率） | ≤ 0.10 | 防幻觉/越权是交付红线 |
| 闲聊 | 误入知识库率 | = 0 | 领域护栏职责 |

**判定结论规则**：全部达标 → "达到可交付质量"；单项不达标 → 出具差距表与改进排期，不宣称交付。

## 4. 评测流程与可复现性

1. **环境准备**：Milvus 可用；BGE-M3 / bge-reranker 模型已加载；LLM API Key 有效；联网与天气/路线工具按需开关（未配置时工具自动降级，用例预期相应调整）。
2. **运行前快照**：记录 `git rev-parse HEAD`、语料文件数（`file_manage_service` 列出的 file_title）、`.env` 中模型/Key 配置名（**不回填 Key 明文**）。
3. **执行**（每条用例独立 session_id，互不污染）：
   ```bash
   # 项目 .venv 下执行（服务需已由 PyCharm 启动或依赖可达）
   python data/eval/run_eval.py --cases data/eval_cases.json --out output/eval/run_$(date +%Y%m%d_%H%M%S)
   ```
   执行器对每条用例调用 `unified_query_app.invoke({session_id, original_query, is_stream:False, domain:""})`，抓取：路由 domain、最终 `answer`、`reranked_docs`（取 file_title 前 5）、规划类的 `tool_weather`/`tool_route`/行程文本；单条超时 90s 判负并记录。
4. **消融对照（同数据同问题，证明链路增益）**：
   - B1 基线：仅稠密向量 Top5（绕过 BM25/多改写/RRF/Rerank）；
   - B2 基线：向量 + BM25 + 多改写 → RRF Top5（无 Rerank）；
   - B3 全链路（现状）。
   实现：执行器 `--ablation` 复用同一 `milvus_gateway` 与 rerank/rrf 服务组件复现 B1/B2，保证除被消融环节外其余完全一致。输出三列 P@5/R@5/F1@5 对比表 → 多路 + RRF + 重排增益 = 量化"好在哪里"的第一证据。
5. **通用 LLM 语义对照（可选，小样本）**：同一批正例交给"无知识库的通用对话 LLM"，记录幻觉率、无出处率、答非所问率（定性 + 样例，不做完整指标，控制成本）。
6. **出报告**：结果 JSON + 汇总 MD 落盘 `output/eval/<时间戳>/`，并把指标表、失败明细、人工复核记录、结论回填进本文档第 5 节。

### 5D.2 判据迭代教训（P3 三条）
