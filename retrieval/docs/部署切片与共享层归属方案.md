### 1.4 "两端共用 27" 的真相：配置聚合器造成虚假共用

- `app/infra/config/__init__.py:6` 一次性聚合 8 个配置单例：`providers.py:11-19`（llm/embedding/reranker/mcp/milvus/mineru/minio/app）。
- 两端都 `from app.infra.config import settings`（`import_server.py:34`、`query_server.py:32`）→ **8 个配置在两端进程里全部实例化**，于是 10 个 config 模块全部被判为"共用"。
- **但不构成部署阻塞**：各 config 只用 `env_str`/`env_bool`（`common.py:19-24`、`:33-45`），**缺 env 时返回 `""`/默认值，不抛异常**。即查询端部署不带 MinIO/MinerU 配置也不会启动失败。
- 真正代价：① 启动载入无用配置对象；② 无法在启动期发现"本端必需配置缺失"（要等运行时才炸）。

## 二、方案设计

### 2.1 部署切片（三选一）

| 方案 | 做法 | 收益 | 代价 / 风险 |
|---|---|---|---|
| **甲·进程级切片 + 启动自检（推荐）** | 不动目录结构。加 `APP_ROLE=import\|query\|gateway`，启动时按角色校验本端必需配置（缺失立即报明确错误）；补 3 份 `Dockerfile` + `docker-compose.yml` + 部署清单文档 | 部署边界清晰、启动期暴露配置错误、可直接容器化 | 共享层文件仍在两端都存在（但进程隔离，无实际影响） |
| 乙·共享层按端物理分包 | 把导入端专用 3 个 / 查询端专用 3 个模块移出 `app/shared` 到各自端目录；`infra_config` 改懒加载按端裁剪 | 物理隔离彻底 | 需改 33 模块 import 路径，回归面大；收益有限（进程本就隔离） |
| 丙·拆双仓 / 双子包 | 拆成两个可独立部署的包 | 最彻底 | 工作量大，与"移动端优先"目标不直接相关，且会重复维护共享层 |

**推荐甲的理由**：部署切片的本质是**进程级隔离**，而非文件级隔离。两端本就是独立进程、独立端口、独立依赖组；共享层文件在两端都存在于磁盘上并无害。真正的痛点是"启动期不知道配置缺不缺"和"没有可复现的部署资产"，甲正好解决这两个。

### 2.2 共享层归属收尾

- 产出 `docs/共享层归属清单.md`：33 模块逐条标注归属 + "两端共用"说明。
- 补**约定**（写入项目 MEMORY）：新增共享层模块的归属判定规则 —— 先写进 `app/shared`，被单端引用满一个迭代周期且确认另一端永不需要，再下沉到端目录；避免"提前优化式"搬迁。
- 顺手清理：`providers.py` 末行 `print(infra_config.app.import_app_name)` 是调试残留，每次 import 都打印。

### 2.3 鉴权 / 限流设计（为 T12 打基础，本任务只出设计不落地）

**身份链路（微信小程序）**
1. 小程序 `wx.login()` → `code`
2. 网关 `POST /auth/login {code}` → 微信 `jscode2session` 换 `openid`
3. 首次登录建 `user_id`（UUID），存 `openid ↔ user_id` 映射到 MongoDB（复用 `mongo_history_utils`）
4. 网关自签 JWT（access 2h + refresh 30d），后续请求 `Authorization: Bearer`
5. `SESSION_OWNER[session_id] = user_id`（现有占位直接复用，接上长期记忆）

**限流（拒绝式，非阻塞）**

| 维度 | 配额建议 | 超配额行为 |
|---|---|---|
| 单 user_id QPS | 2 req/s（生成类接口成本极高） | HTTP 429 + `Retry-After` |
| 单 user_id 日配额 | 200 次/天（可按套餐调整） | HTTP 429 |
| 单 IP QPS | 10 req/s（防刷） | HTTP 429 |

- 存储选型：**依赖 T9 的 Redis**（跨进程共享计数，原子 INCR + TTL 滑动窗口）。若 T9 未做，先单机内存令牌桶（多副本部署会失效，仅本地联调可用）。
- 与现有限流器关系：`rate_limit_utils` 保持**出站专用**（保护第三方 API），新增入站限流器另起，二者不混用。

**分层防护衔接**：T10 把 T4 的 `egress_sanitizer`（脱敏/白名单/注入拦截）接入 `gateway_guard()`，本设计的鉴权/限流是其**前置层**（先认证 → 再限流 → 后防护 → 转发）。
