# 分布式开发拆分计划

> 目标：项目将长期构建为企业级（约 1 年周期），当前 `app/` 已 197 个 .py 文件 / 约 2.1 万行，整体含 test/data 约 2.3 万行。本计划让代码做到**可多人分布式并行开发**，同时保持运行时架构稳定。

---

## 0. 两个已拍板工程决断（本节确认沿用）

1. **运行时：单 Agent + 多 Skill，不拆多 Agent。**
   - 依据：框架"多 Agent 不是默认选项"；多 Agent 引入状态同步/调试负担，与项目规模无关。
   - **澄清**：此处"不拆"指运行时推理架构。代码层必须做**强模块化**，分布式开发靠模块边界实现，二者不矛盾。

2. **模型路由：三档语义化能力档，由 B1 输出 `model_tier` 驱动。**
   - 档位命名（修正自原 `cheap/strong/long_ctx`，避免误导为"价格档"）：
     - `lite` —— 简单检索问答 / 闲聊（低复杂、短上下文）
     - `standard` —— 多步推理 / 规划
     - `longctx` —— 长文档 / 长对话 / 大上下文
   - 由 B1（意图路由 LLM 化，序6）单次输出 `model_tier`；Harness 层（序7 `pkg-model`）负责 tier → 具体模型 + 供应商 + 熔断 + 降级映射。框架精神：按**能力**而非**价格**路由。

### 1.1 反向依赖清单（✅ 已归零：2026-09-10 整改 15→0）
运行 `scripts/check_import_direction.py` 抓出 15 处违反 `api→process→rag/infra→shared` 方向的 import，是分布式开发的耦合地雷：

> ✅ **已归零（2026-09-10）**：通过三项整改——① `app/api/schemas` 下沉 `app/shared/schemas`；② `warmup` / `data_version_service` 改为依赖反转（钩子注册表，由新建 `app/api/bootstrap.py` 在启动时注册具体实现）；③ `current_date_text` 下沉 `app/shared/runtime/date_utils.py`。`scripts/check_import_direction.py` 现输出「未发现反向依赖」。下方为整改前基线清单：

- **shared → rag/infra（10 处，最严重）**：`shared/runtime/warmup.py` 8 处、`data_version_service.py` 2 处。底层预热/版本服务反向依赖业务层——应反转依赖（预热逻辑下沉到各域 `pkg-*` 自注册，或 shared 仅定义钩子接口由域实现）。
- **rag → api/process（4 处）**：`trip_plan/*` 3 处 import `api.schemas`/`process`；`tourism_query/itinerary_service.py` 1 处 import `process`。根因：`api/schemas` 是 Pydantic DTO，按理属 `shared` 或独立 `pkg-schemas`，放在 `api` 包下导致业务层反向依赖 api。
- **process → api（2 处）**：`trip_plan/*` import `api.schemas`。同上，schemas 下沉即可解。

**整改方向（阶段 A 具体项）**：
1. 将 `app/api/schemas` 下沉为 `app/shared/schemas`（或独立 `pkg-schemas`），消除 rag/process 对 api 的反向依赖（解 5 处）；
2. `warmup.py` / `data_version_service.py` 改为钩子反转依赖（解 10 处）。

## 2. 拆分总原则

- **P1 运行时单 Agent + 多 Skill**（沿用决断①）。
- **P2 代码层强模块化**：每个能力 = 独立包，暴露 `service.py` 门面；跨包**只依赖门面**，不依赖内部模块。
- **P3 依赖方向单一**：`api → process/orchestration → rag/infra → shared`。禁止反向依赖与横切（尤其禁止 `common` 反向 import 业务包）。
- **P4 契约优先**：包公开接口 = 冻结契约 + 输入输出 schema + 文档；门面签名变更须 review。
- **P5 可独立测试 + CI**：每包独立 `test/`，CI 可单包跑；pre-commit 做 import 方向 lint。

## 3. 目标包结构（Domain Packages）

当前仍是单仓库 monorepo，包以"逻辑边界 + import 规则"实现，**不立即物理拆分**。

| 目标包 | 归并现有代码 | 并行度 |
|---|---|---|
| `pkg-api` | app/api/http（4 server + mobile BFF） | 中（依赖 orchestration 契约） |
| `pkg-orchestration` | app/process/unified_query + intent_route + B1 LLM 路由 | 低（中枢，专人） |
| `pkg-retrieval` | vectorstore / bm25 / rerank / split / text_parse | 中（先冻结契约） |
| `pkg-domain-tourism` | app/rag/tourism_query + tourism_import | **高（完全并行）** |
| `pkg-trip` | app/rag/trip_plan 子图 | **高（完全并行）** |
| `pkg-ingest` | 导入侧 + 4 外发出口 + egress_gateway | 中 |
| `pkg-infra` | amap/weather/rail/egress/vectorstore/object_storage 网关 | 低（中枢，专人） |
| `pkg-model` | **新增** model_gateway（model_tier 路由 + 熔断，序7） | 低（中枢，专人） |
| `pkg-shared` | runtime / logger / cache / history | 低（最底层，先冻结） |

## 4. 阶段路线

- **阶段 A（现在，零风险）**：逻辑包边界 + 公开接口契约 + import 方向 lint + 每包 `test/`。仍是单 repo，但结构和 CI 已支持多人并行开发。
- **阶段 B（规模更大 / 团队扩编时）**：按包拆 git submodule 或内部 PyPI，真正物理分布式；门面契约作为包间 API 版本管理依据。

---

## 5. 接口契约规范（推广现有门面范式）

- 每个包提供 `service.py` 作为唯一公开入口（参照 `egress_gateway.py` 单例门面写法）。
- 跨包调用一律 `from app.pkg_x.service import do_y`，禁止 `from app.pkg_x.internal_module import ...`。
- 每个包含：`README.md`（职责 + 公开 API + 输入输出 schema）+ 门面签名 frozen 标记。
- `pkg-retrieval` / `pkg-shared` / `pkg-infra` 是底层中枢，**先冻结契约**再放开并行。

## 7. 与现有执行顺序（序 0–15）的关系

拆分是**横切工程基础设施**，不是新增阻塞序。建议在序 0 之前或并行建立"包边界 + 契约 lint"，使后续每个序都能在独立包内并行推进。不新增主线阻塞项。

---

## 8. 立即可做的最小动作（本回合可落地，零风险）

1. **import 方向检查脚本** `scripts/check_import_direction.py`：静态扫描 `from app...` 导入，校验是否符合 `api→process→rag/infra→shared` 方向，违反则 CI 失败。接入 pre-commit。
2. **`pkg-common` 契约冻结标记**：给 `intent_route_service` / `rerank` / `bm25` / `text_parse` / `split` 的门面函数加 `# CONTRACT-FROZEN` 注释，变更须 review。
3. **每包 `test/` 骨架**：为 6 个高并行度包先建空 `test/` + `pytest` 配置，后续按序填充。

> 注：物理代码移动（把文件搬进 pkg-* 目录）是重活，建议留到阶段 A 基建（lint + 契约）就绪后，按包分批执行，每批伴 40 题回归护栏。
