## 一、现状痛点（代码定位）

**要求与能力自相矛盾**：

| 位置 | 事实 |
|---|---|
| `app/resources/prompts/tourism/itinerary_out.prompt:3` | 行程输出结构**强制要求**：「交通方式与在途时长」+「花销预估」 |
| `app/rag/tourism_query/itinerary_service.py:86-92` | `_strip_flight_train_numbers()` **主动剥离** LLM 编造的航班号/车次号 |
| `app/rag/tourism_query/itinerary_service.py:309` | 输出前统一调用剥离：`_compact_itinerary(_strip_road_chains(_strip_flight_train_numbers(...)))` |
| `answer_out.prompt:9` | 已约定：实时票价无数据时须说明无法确认并建议核实，不得编造 |

即：**系统要求给交通方式与花费，却没有可信数据源，只能靠模型估算，且车次号因不可核实被删掉**。
结果就是跨城行程只能泛泛写"可乘高铁前往，约 X 小时"——时长与路费均不可靠。

**已有能力对照**：驾车路线（高德 `route_tool_service`）、天气（和风/高德 `weather_gateway`）都已有真实数据源，
唯独**跨城公共交通（火车/高铁）是空白**——这正是 T14 要补的最后一块拼图。

## 三、接入设计（推荐自部署 `drfccv/mcp-server-12306`）

### 3.1 网关：`app/infra/rail_gateway.py`（照 amap/weather 既有范式）

```
rail_gateway.query_trains(origin, destination, date)
   │  主源：自部署 12306-MCP（Streamable HTTP，容器内服务名 rail-mcp）
   │  失败/超时 → 降级 source="unavailable"，ok=False，不抛异常、不阻断主链路
   ▼
归一化输出：{ trains: [{code, from, to, depart, arrive, duration,
                       fares:{二等座, 一等座, 商务座}}],
              fetched_at, source }
```

- 与 `weather_gateway`（主和风/备高德）同构：**主备降级 + 失败留痕不冒充**
- 遵守项目约定：工具一律"失败降级 `ok=False`、不抛异常、不阻断主链路"
- 超时建议 6s（对齐 `AMAP_TIMEOUT`），进程内缓存复用 `cached_invoke`（namespace=rail）

### 3.2 行程链路接入点

| 环节 | 改动 |
|---|---|
| `node_tool_route`（高德驾车）旁 | 并行增 `node_tool_rail`，静态边汇入 `node_rrf`（复用规划分支既有并行模式） |
| `itinerary_out.prompt` | 增【铁路参考】区块，与【实时天气参考】【路线参考】并列 |
| `_strip_flight_train_numbers` | **从"一律剥离"改为"仅剥离未在【铁路参考】中出现的班次"** —— 这是 T14 的核心收益：真实车次得以保留 |
| 花销预估 | 交通费以【铁路参考】票价为准；缺失时维持现状（不给具体数字，提示自行核实） |

### 3.3 反编造护栏（硬约束，不可让步）

- 票价/车次输出**必须**附：`数据时间 + "以 12306 官方为准"`
- 【铁路参考】为空时，**严禁**模型自行估票价（沿用 `answer_out.prompt:9` 口径：说明无法确认并建议出行前核实）
- 评测硬约束不变：**Acc 1.0 不编造**；票价值不得由模型生成

## 四、风险与降级

| 风险 | 影响 | 应对 |
|---|---|---|
| 非官方接口失效/改版 | 铁路数据全不可用 | 网关降级 `ok=False`，行程回到当前表现（泛化表述），**不阻断主链路** |
| 高频调用被限流 | 部分请求失败 | 进程内缓存 + `AMAP_MIN_INTERVAL_MS` 同款节流器 |
| 数据经第三方 | 合规风险 | 自部署（不托管），容器内私有网络，与导入侧 egress 审计范式一致 |
| 票价浮动导致误导 | 用户按旧价做决策 | 强制标注数据时间 + 官方核实提示 |

**退路**：若自部署验证不通过，退化为"沿用现有剥离逻辑 + 提示用户自行到 12306 查询"，
**绝不可让模型凭空编造车次与票价**。

## 六、可用性验证结果（2026-09-10 实测，✅ 通过）

> 即实施步骤第 1 步「先验证后写代码」——**已跑通，数据真实可用**。

**启动方式（本机实测，无需 Docker）**：

```bash
SERVER_PORT=8010 uvx --from mcp-server-12306 mcp-12306     # 首次会下载依赖，约 2 分钟
# 备选（Docker，需 daemon 在跑）：docker run -d -p 8010:8000 drfccv/mcp-server-12306:latest
```

- `GET /health` → `{"status":"healthy","stations":3384,"active_sessions":0}`
- `GET /` → 版本 `0.5.0.post20260822`，7 个工具：`query-tickets / query-ticket-price / search-stations / query-transfer / get-train-route-stations / get-train-no-by-train-code / get-current-time`，端点 `/mcp`

**调用方式**：项目**已装 `mcp` SDK**（`app/rag/common/web_search_service.py:14-15` 在用），**无需新增依赖**，直接照抄既有范式：

```python
transport = streamable_http_client("http://127.0.0.1:8010/mcp", http_client=httpx2.AsyncClient(...))
async with Client(transport, mode="legacy") as client:
    await client.call_tool("query-ticket-price", {"from_station": "深圳", "to_station": "成都", "train_date": "2026-09-11"})
```

**实测数据（深圳→成都，2026-09-11）**：

| 场景 | 结果 | 耗时 |
|---|---|---|
| `query-tickets` | 7 班车（G/Z/D 混合），含各席别余票 | **1.57s** |
| `query-ticket-price` | 7 班车各席别**真实票价**：G2942（深圳北→成都东）二等座 **813.5** / 一等座 1281.5 / 商务座 2717.5；Z332 硬座 240 / 硬卧 436 | **1.52s** |
| 无效车站（"不存在的站"） | `{"success": false, "error": "车站名称无效", "suggestions": [], "hint": "..."}` —— **结构化错误、不抛异常** | 0.01s |

**结论**：数据真实、延迟 ~1.5s（稳在 6s 超时预算内）、错误形状规整 → **满足接入条件**。

**⚠️ 实测发现的字段坑（写 `rail_gateway` 必读）**：两个端点命名**不一致**——

- `query-tickets` → 车次号在 **`train_no`**（如 `G2942`），票务在 `seats`
- `query-ticket-price` → 车次号在 **`train_code`**（其 `train_no` 是内部哈希串如 `6i000G294203`），票价在 `prices`

网关归一化**必须取 `train_code`**；若误用 `train_no` 会把内部哈希当车次号输出，`_strip_flight_train_numbers` 也匹配不到，反而把乱码暴露给用户。

**取证脚本**：`logs/_tmp_verify_12306.py`、`logs/_tmp_verify_12306_price.py`（logs/ 已 gitignore）。

## 九、容器化（2026-09-10 补，贴合移动端 / 双机部署）

**背景**：Docker daemon 当时未启动，故验证期走 `uvx`；上线后服务跑在服务器上，容器化的「内网互访、不暴露端口、崩溃自愈、镜像可复现」正是生产所需。

**上游镜像情况（实测核对）**：`drfccv/mcp-server-12306` 仓库**自带 `Dockerfile`**（python:3.12-alpine 多阶段，`uv sync`），但**未在 Docker Hub 发布官方镜像**——故**自建镜像**，不依赖第三方 tag。

**产物**：

| 文件 | 内容 |
|---|---|
| `Dockerfile.rail-mcp`（新） | `python:3.12-slim` + `pip install "mcp-server-12306[http]"`（extra 不存在则回退基础安装）+ `HEALTHCHECK /health` + `CMD ["mcp-12306"]`；监听 `0.0.0.0:8000` |
| `docker-compose.yml` | 新增 `rail-mcp` 服务（`profiles:["infra"]`），映射 **8010:8000**，`restart: unless-stopped` |

**双形态端点一致性**（关键设计）：

| 形态 | 启动 | `RAIL_MCP_URL` |
|---|---|---|
| 本机开发 | `SERVER_PORT=8010 uvx --from mcp-server-12306 mcp-12306` | `http://127.0.0.1:8010/mcp` |
| 容器部署（query 同网络） | `docker compose --profile infra up -d rail-mcp` | `http://rail-mcp:8000/mcp` |
| 容器部署（query 跑本机） | 同上（映射 8010→8000） | `http://127.0.0.1:8010/mcp` |

即：**两种形态切换只改 `.env` 一行，零代码改动**。

**运维命令**：
```bash
docker compose --profile infra build rail-mcp    # 构建（首次约 1~2 分钟）
docker compose --profile infra up -d rail-mcp    # 启动
curl http://127.0.0.1:8010/health                # {"status":"healthy","stations":3384,...}
docker compose --profile infra logs -f rail-mcp  # 跟日志
```

**未验证项（诚实标注）**：本轮 Docker daemon 未启动，**镜像未实际构建/运行**；仅完成 `docker compose config` 语法校验（`EXIT=0`，服务解析正常）。首次真机构建时需确认 `pip install "mcp-server-12306[http]"` 的 extra 名（若报错，Dockerfile 已内置回退为无 extra 安装）。
